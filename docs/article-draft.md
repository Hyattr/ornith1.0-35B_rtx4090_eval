# 35BのローカルLLMを4090で評価したら、モデルより先に自分の計測が壊れていた

RTX 4090 を1枚だけ積んだマシンに 35B のコーディングエージェントモデルを載せて、速度と実力を測りました。この記事はその記録です。

結論から書いてしまうと、モデルは速度も精度も期待以上でした。ただ、この記事で本当に書きたいのはそこではありません。測っている途中で、**自分の計測方法のほうが二度も壊れていた**ことに気づいた、という話です。

一度目は、物理的にありえない数字が出たので気づけました。二度目はもっとたちが悪くて、モデルの点数が不自然に低く出ただけでした。危うくそのまま「このモデルはこの程度」と書いて公開するところだったのです。

どちらも、ローカルLLMのベンチマーク記事を書こうとすれば普通に踏む罠だと思います。計測で出てきた数字そのものより、そちらのほうが役に立つのではないでしょうか。

---

## 何を測ったのか

測った対象は **Ornith-1.0-35B** です。DeepReinforce Team が MIT ライセンスで公開しているモデルで、**エージェント型のコーディング特化**を謳っています。Gemma 4 と Qwen 3.5 の上に追加学習（post-training）された MoE モデルで、公称ベンチマークも Terminal-Bench 2.1 や SWE-bench といった、コードとエージェント系のものだけが並びます。

つまり、**日本語の一般知識で測ってはいけないモデル**です。ここを外すと、用途違いの低スコアを取っておいて「このモデルは弱い」と書いてしまうことになります。そこで評価軸は、コード生成とツール利用に寄せました。

```
モデル      : Ornith-1.0-35B-UD-IQ4_XS (unsloth 版 GGUF)
アーキテクチャ : qwen35moe (MoE) / vision対応 / ツール利用向け学習済み
量子化      : UD-IQ4_XS  ※均一4bitではなくレイヤーごとにビット幅可変
コンテキスト  : 32,768 (ネイティブは 262,144 なので 1/8)
サーバー     : LM Studio
マシン      : RTX 4090 (VRAM 24GB) / Core i9-14900KF / RAM 64GB
サンプリング  : temperature 0.6 / top_p 0.95 / top_k 20 (モデルカード推奨値)
```

ひとつ強調しておきたいのは、モデルカードが推奨している構成は **8×80GB の GPU ノード**、コンテキスト長 262,144 だということです。今回はそれに対して、24GB のGPUが1枚、4bit 量子化、コンテキスト長は 1/8。**まったく違う土俵で動かしています**。以下の数字は、その前提で読んでください。

## まず速度：35B とは思えない速さ

入力の長さを変えながら、最初のトークンが返るまでの時間（TTFT）、入力の処理速度、生成速度を測りました。

| 入力トークン | TTFT | 入力処理 | 生成速度 |
|---:|---:|---:|---:|
| 316 | 0.092秒 | 3,418 tok/s | **137.8 tok/s** |
| 4,308 | 0.639秒 | 6,741 tok/s | 136.4 tok/s |
| 8,568 | 1.216秒 | 7,044 tok/s | 134.1 tok/s |
| 17,117 | 2.462秒 | 6,954 tok/s | 130.5 tok/s |
| 25,669 | 3.780秒 | 6,790 tok/s | **127.2 tok/s** |

生成速度は、最も速い条件で **137.8 tok/s** 出ました。25,000 トークンを詰め込んだ状態でも 127.2 tok/s で、劣化は 7.7% に留まっています。

「35B が 4090 一枚でこの速度?」と思われるかもしれませんが、これは **MoE（Mixture of Experts）だから**です。MoE はモデルの内部を複数の「エキスパート」に分けておき、トークンごとにその一部だけを使います。総パラメータが 35B あっても、1トークンあたりに実際に計算される量はずっと小さくて済むわけです。**「35B」という数字を、パラメータを毎回すべて使う密なモデルと同列に語ると誤解します。**

入力の処理速度のほうは、約 7,000 tok/s あたりで頭打ちになりました。TTFT は入力の長さにほぼ比例して伸びています。

もうひとつ、測っていて意外だったのが VRAM です。入力が 316 トークンのときも 25,669 トークンのときも、**空き容量は 3,284 MiB のまま 1MiB も動きませんでした**。LM Studio はモデルをロードする時点でコンテキスト長のぶんの KV キャッシュ（生成中の途中結果を置いておく領域）を確保しているようで、実行中に増えることはありません。つまり、**長い入力を投げている途中で VRAM が枯渇する心配は要らない**ということです。動くか動かないかは、ロードした時点ですでに決まっています。

## 罠その1：41倍の嘘をついていた

> トークン・キャッシュ・出力上限の仕組みそのものは、別記事に基本から書きました → https://note.com/hyattrt/n/nfb5375d04807

上の速度の表は、実は一度作り直したものです。最初の計測は、全部やり直しになりました。

各条件で同じプロンプトを5回ずつ投げて平均を取る、というよくあるやり方をしていたのですが、回ごとの結果を並べてみるとこうなっていました。

| 入力 | 1回目 TTFT | 2〜5回目 TTFT |
|---|---:|---:|
| 4,309 トークン | 0.579秒 | 0.058秒 |
| 8,569 トークン | 1.164秒 | 0.059秒 |
| 17,119 トークン | 2.422秒 | 0.059秒 |
| 25,669 トークン | 1.462秒 | 0.061秒 |

2回目以降が、**入力の長さに関係なく一律 0.058秒**です。ここから入力処理速度を逆算すると **419,000 tok/s** になります。物理的にありえない数字です。

犯人は **LM Studio のプロンプトキャッシュ**でした。同じ入力を繰り返し送れば、2回目以降は処理済みの結果を使い回します。サーバーとしてはまったく正しい動作です。速く返ってきているのは事実で、ただそれは「モデルが入力を処理する速さ」ではありません。

さらに悪いことが、もうひとつありました。ダミーの長文入力を、共通の雛形から長さだけ変えて生成していたのです。そのせいで、**24k のプロンプトが 16k のプロンプトの先頭部分をそのまま含んでいました**。キャッシュは先頭からの一致で効くので、条件をまたいでヒットしてしまい、24k の初回（1.462秒）が 16k の初回（2.422秒）より速い、という逆転まで起きています。表の一番下の行だけ数字が飛んでいるのは、そのためです。

修正は単純で、実行するたびにプロンプトの**先頭**を一意な文字列にすることです。キャッシュは接頭辞の一致で効くので、末尾に乱数を足しても意味がありません。

### 転んだついでに、キャッシュの効果そのものを測ってみた

せっかく引っかかったので、このキャッシュの効果自体を測りました。同じプロンプトを2回投げて、1回目（cold）と2回目（warm）を比較します。

| 入力トークン | cold | warm | 高速化 |
|---:|---:|---:|---:|
| 1,093 | 0.220秒 | 0.057秒 | 3.9倍 |
| 4,306 | 0.639秒 | 0.057秒 | 11.2倍 |
| 17,115 | 2.470秒 | 0.060秒 | **41.0倍** |

warm 側は入力の長さによらず約0.06秒で一定なので、**入力が長くなるほど実態との差が開いていきます**。17k トークンでは41倍でした。

言い換えると、同じ入力を繰り返し投げる評価スクリプトは、**実態の1/41の速さを「計測結果」として報告します**。しかもエラーは一切出ません。ただ、いい数字が出るだけです。

なお、この罠が効くのは入力の処理だけです。**生成速度と思考トークンの量は影響を受けません。** 速度を測っていてキャッシュを疑うべきなのは TTFT と入力処理速度の側だ、と覚えておくと切り分けが速くなります。

## 罠その2：モデルの点数だと思っていたものが、自分の設定ミスだった

> 出力トークンの上限（`max_tokens`）まわりの話が続きます。仕組みから知りたい方は、こちらの基礎編をどうぞ → https://note.com/hyattrt/n/nfb5375d04807

ここからが本題です。まず仕組みの話から始めます。

### 「考える」ぶんも、出力の予算から引かれる

このモデルは reasoning モデルで、答えを返す前に内部で「思考」を生成します。そして、**この思考も出力トークンとして予算を消費します**。画面に出てこないので数のうちに入らない気がしますが、しっかり入ります。

いちばん単純な例で見てみます。「PONG とだけ答えて」という、合図に対して決まった一言を返すだけの指示です。まずは予算に余裕がある場合（`max_tokens=1024`）から。

```
reasoning     : 146トークン
content       : "PONG"
finish_reason : "stop"
```

**4文字を出すのに、思考が146トークン。** では、予算を 128 に絞るとどうなるか。

```
max_tokens    : 128
reasoning     : 128トークン   ← 全部を思考で使い切った
content       : ""            ← 空
finish_reason : "length"
```

思考だけで予算を使い切ってしまい、回答が始まる前に生成が終わりました。ここで重要なのは、**これがエラーとして扱われない**ことです。「正常に、上限まで出力しました」という顔をして、中身が空のレスポンスが返ってきます。

ではどのくらいの予算があれば空にならないのか。`max_tokens` を変えながら、空応答が出る割合を測りました（各5回）。「中程度の課題」は、「時速の平均を求めて、数値だけ答えよ」という一問だけの算数の文章題です。

| max_tokens | 「PONGと答えて」 | 中程度の課題 |
|---:|---:|---:|
| 64 | 100% | 100% |
| 128 | 60% | 100% |
| 256 | **0%** | 100% |
| 512 | 0% | 60% |
| 1024 | 0% | **0%** |

**「PONGと答えて」に、256トークンの予算が必要でした。**

実用上、ここが一番危ないところです。評価スクリプトがこれを検出せずにそのまま集計すると、**自分の設定ミスが「不正解」として記録され、モデルの性能を過小評価します**。`finish_reason == "length"` かつ `content == ""` のレスポンスを、失敗として弾く処理は必須です。

（ちなみに `finish_reason` が `"tool_calls"` のときも `content` は空になりますが、そちらは正常な動作です。空だという理由だけでまとめて弾いてしまうと、正常なツール呼び出しまで失敗扱いになってしまいます）

### そして、予算の見積もりを二度外した

思い込みが外れたのは二度です。

一度目が、いま見た「PONGと答えて」でした。単純な指示なら予算は要らないはずだ、という感覚がそのまま外れています。実際には256トークン必要でした。

二度目が本番です。上のデータから「これだけ思考するとしても、難しい問題で 4096 あれば十分だろう」と見積もって、コード生成12問を回しました。結果がこれです。

```
t01_duration   easy    思考 4096 / 回答 0字   ← 最も簡単な問題
t06_flatten    medium  思考 4096 / 回答 0字
t10_diff       hard    思考 4095 / 回答 0字
t08_cycle      hard    思考 3852 / 回答 982字 (途中で打ち切り)
```

**12問中4問が、予算の上限に達していました。** うち3問は回答が完全に空で、1問は書いている途中で切れています。

空応答は、採点すると1点になります。その結果、平均スコアは 3.58 でした。もしここで気づかずに公開していたら、「**35Bのコーディング特化モデルにコードを書かせたら、5点満点で3.6点だった**」という、数字そのものは本物なのに結論だけが完全な嘘、という記事ができあがっていたことになります。

予算を 16384 に上げて回し直したところ、全12問が完走して平均は **4.75** になりました。**測っていたのはモデルの実力ではなく、私の設定ミスでした。**

### なぜ見誤ったのか

原因を調べてみたら、想定していなかった事実が出てきました。出題するときに自分で付けた難易度のラベルごとに、思考トークン数を集計したものです。

| 出題時のラベル | 思考トークン中央値 | 範囲 |
|---|---:|---|
| **easy** | **8,937** | 7,689〜10,185 |
| medium | 3,033 | 2,351〜8,118 |
| hard | 3,510 | 1,246〜5,313 |

**最も簡単なはずの問題が、最も多く思考していました。**

「ソート済みのリスト2本をマージする」に **10,185トークン**。「`1h30m` のような文字列を秒に変換する」に 7,689トークン。その一方で、最難関に分類した「スレッドの競合を説明して直せ」は 1,246トークンで終わっています。

理由は推測になりますが、実装課題ではエッジケースの列挙（空文字列、未知の単位、空リスト、O(n)の制約……）で思考が膨らみ、デバッグ課題は正解が一意に決まるぶん早く収束するのだと思います。検証はしていないので、あくまで推測です。

いずれにしても、実用上の結論ははっきりしています。**問題の見た目の難しさから `max_tokens` を見積もる方法は成立しません。** コーディング用途なら、最初から 16384 を確保しておくのが安全です。

## で、実力はどうだったのか

前置きが長くなりました。ここからが計測結果です。

### ツール呼び出し：100%（60/60）

5種類のツールを定義して、20シナリオを各3回ずつ試しました。

| 区分 | 精度 |
|---|---:|
| 呼ぶべき場面 | 100% |
| 呼ぶべきでない場面 | 100%（**誤検知 0%**） |

ツールの選択ミス、引数のミス、呼ぶべきでない場面での誤検知が、**1件もありません**。

テストに含めた観点は、5種類の中から適切なものを選べるか、引数を正確に埋められるか、一般知識の質問に対してツールを呼ばずに答えられるか、「テストファイルを列挙して、実行はするな」という指示から `search_files` を選べるか、そして「そのうちチームに知らせないと」という独り言に対して**勝手に `send_email` を呼び出さないか**。全部通りました。

### JSON スキーマ準拠：100%（60/60）

ネストしたオブジェクト、enum による値の制限、配列、`additionalProperties: false` を含むスキーマを用意して、各30回ずつ出力させました。

結果は、**プロンプトで指示するだけで 100% 準拠**。`response_format` によるフォーマット強制は必要ありませんでした。JSONを `` ```json `` のフェンスで包んで返してしまう挙動も、1件もありません。ローカルLLMでは「JSONで返せと言ったのにマークダウンで返ってくる」が定番の失敗ですが、それが皆無でした。

### 正直に書くと、この2つは天井に張り付いています

100%、100%。並べると強そうに見えますが、**これは私のテスト設計の識別力が足りていないということです。**

ここから分かったのは「基本的なツール判断とJSON出力では破綻しない」という下限であって、**このモデルがどこで壊れるのかは測れていません**。満点を成果として誇るよりも、天井に当たってしまったこと自体を書いておくべきだと思っています。

### コード生成：4.75 / 5.00

12問を出しました。LRUキャッシュ、トークンバケット、リトライのデコレータ、有向グラフの閉路検出、LCSベースのdiff、ストリーミング中央値、スレッド競合の説明、意図的に壊したコードの修正、といった内容です。

**12問中10問が満点。** これは素直に強いと思います。

## 審査員を2つ使った話

コード生成の採点は、Claude（claude-opus-5）と Gemini（gemini-3.8-flash）に、**それぞれ独立してやらせました**。

理由は冗長化ではありません。**審査員が1つだと、その採点自体が妥当だったのかを誰も検証できない**からです。読む側からすると、「Claude がそう言っているから」以上の根拠が得られません。

2つあれば、一致率という検証可能な数字が出せます。

| 指標 | 値 |
|---|---:|
| 完全一致 | **91.7%**（11/12） |
| ±1以内 | 100% |
| 平均スコア差 | 0.08（Claude 4.75 / Gemini 4.83） |

### 両者が同じ誤りに、独立にたどり着いた

最低スコアだった問題が面白かったので書いておきます。

課題は「重複を含むソート済みリストに対して最初の出現位置を返す二分探索のコードに欠陥がある。それを指摘したうえで、**実際に欠陥が再現する入力**を挙げ、修正版を示せ」というものでした。

Ornith は、**欠陥の診断も修正コードも正しく**書きました。ところが、再現する入力のほうを間違えます。`xs = [1, 2, 2, 3], target = 2` を挙げて「期待される返り値は 0 だ」と主張したのですが、`xs[0]` は 1 なので、2 が最初に現れるのは index 1 です。この入力に対しては、元のコードの返り値のほうが正しいことになります。

両方の審査員が、これを独立に指摘しました。

> **Claude**: 有効な再現入力は `[2, 2, 3]` のようなものになる。課題が具体的な再現入力を明示的に求めている以上、修正が妥当でもこれは実質的な欠陥である。

> **Gemini**: モデルは最初の出現が index 0 だと誤って主張しているが、`xs[0] == 1` である。

系統のまったく違う2社のモデルが、独立に、同じ細かい誤りにたどり着いたわけです。これは**採点が機能していることの証拠**であり、同時に **Ornith の弱点**でもあります。直し方は分かっているのに、自分が挙げた例を検算していない。

### 唯一の不一致も、雑音ではなかった

評価が割れた1問（LRUキャッシュ、Claude 4点 / Gemini 5点）も、中を見ると理由がありました。

Claude は「`capacity=0` という退化したケースで、ダミーノードに対して削除を試みるので KeyError になる。容量の値を検証してもいない」と指摘しています。Gemini はそこまで検証していませんでした。

**どちらかが誤りなのではなく、厳しさの差**です。不一致は平均で均してしまわず、中身を見に行く価値があります。

### 事前に気にしていたバイアスについて

Ornith は **Gemma 4** の上に追加学習されています。Gemma は Google 系のモデルです。つまり、評価される側と Gemini の間には、Claude との間よりも近い血縁がありえます。LLMを審査員に使うときの既知のバイアスとして「自分と同じ系統のモデルの出力を好む」というものがあり、それが **Gemini 側にだけ働く**可能性がありました。

結果は、平均スコア差 0.08。系統的な甘さは観測されませんでした。ただし、**12問で系統差の有無を判断するには数が足りません**。「この規模では検出されなかった」以上のことは書けない、というのが正直なところです。

## まとめ：何が分かって、何が分からなかったか

**分かったこと**

- 4090 一枚 + 4bit量子化で、35B の MoE が **137.8 tok/s** で生成する。25kトークン入れても 127.2 tok/s
- コード生成は **4.75/5.00**。12問中10問が2つの審査員から満点
- ツール呼び出しとJSON出力は、**この難易度では破綻しない**
- 弱点らしきものが1つ。**自分の挙げた例を検算しない**

**分からなかったこと**

- ツール呼び出しとJSON準拠が**どこで壊れるのか**（天井に張り付いてしまい、識別できませんでした）
- 難易度と思考量が逆相関する**理由**（観察しただけで、検証はしていません）
- 審査員の系統バイアスの**有無**（12問では判定できません）
- ネイティブの 262,144 コンテキストでの挙動（24GBでは 32,768 が限界でした）

**測る側の教訓**

1. **プロンプトキャッシュを止めないと、速度は測れない。** 17kトークンで41倍ずれます
2. **問題の難易度から `max_tokens` は見積もれない。** 一番簡単な問題が一番思考しました
3. **空応答を失敗として検出しないと、自分の設定ミスがそのままモデルの点数になる**
4. **審査員は2つ用意する。** 一致率がないと、採点が妥当だったのかを誰も確かめられません

この中では3番目が、この記事で一番書きたかったことです。平均3.58という数字は、私が予算を絞りすぎただけで出たものでした。エラーは出ませんし、レスポンスは正常に返ってきます。**気づく手がかりは「思考トークン数が上限に張り付いている」ことだけ**でした。
