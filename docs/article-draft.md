# 35BのローカルLLMを4090で評価したら、モデルより先に自分の計測が壊れていた

RTX 4090 一枚に 35B のコーディングエージェントモデルを載せて、速度と実力を測った記録です。

結論から言うと、モデルは speed も精度も期待以上でした。ただしこの記事で本当に書きたいのはそこではありません。**測っている途中で、自分の計測方法が二度も壊れていたことに気づいた**話です。片方は「物理的にありえない数字」が出て気づきました。もう片方は、モデルの点数が低く出て、危うくそのまま「このモデルはこの程度」と書くところでした。

同じ罠は、ローカルLLMのベンチマーク記事なら普通に踏みます。数字より、そちらのほうが役に立つと思います。

---

## 測ったもの

**Ornith-1.0-35B**。DeepReinforce Team による MIT ライセンスのモデルで、**エージェント型コーディング特化**を謳っています。Gemma 4 と Qwen 3.5 の上に post-training された MoE モデルで、公称ベンチマークも Terminal-Bench 2.1 や SWE-bench といったコード・エージェント系だけが並びます。

つまり**日本語の一般知識で測ってはいけないモデル**です。ここを外すと、用途違いの低スコアを「このモデルは弱い」と書いてしまいます。評価軸はコード生成とツール利用に寄せました。

```
モデル      : Ornith-1.0-35B-UD-IQ4_XS (unsloth 版 GGUF)
アーキテクチャ : qwen35moe (MoE) / vision対応 / ツール利用向け学習済み
量子化      : UD-IQ4_XS  ※均一4bitではなくレイヤーごとにビット幅可変
コンテキスト  : 32,768 (ネイティブは 262,144 なので 1/8)
サーバー     : LM Studio
マシン      : RTX 4090 (VRAM 24GB) / Core i9-14900KF / RAM 64GB
サンプリング  : temperature 0.6 / top_p 0.95 / top_k 20 (モデルカード推奨値)
```

ひとつ強調しておくと、モデルカードの推奨構成は **8×80GB の GPU ノード**、コンテキスト 262,144 です。こちらは 24GB 一枚、4bit 量子化、コンテキストは 1/8。**まったく違う土俵で動かしている**という前提で読んでください。

## まず速度：35B とは思えない速さ

| 入力トークン | TTFT | 入力処理 | 生成速度 |
|---:|---:|---:|---:|
| 316 | 0.092秒 | 3,418 tok/s | **137.8 tok/s** |
| 4,308 | 0.639秒 | 6,741 tok/s | 136.4 tok/s |
| 8,568 | 1.216秒 | 7,044 tok/s | 134.1 tok/s |
| 17,117 | 2.462秒 | 6,954 tok/s | 130.5 tok/s |
| 25,669 | 3.780秒 | 6,790 tok/s | **127.2 tok/s** |

**生成 137.8 tok/s。** 25,000 トークンを詰め込んでも 127.2 で、劣化は 7.7% に留まります。

「35B が 4090 一枚でこの速度?」と思うかもしれませんが、これは **MoE だから**です。MoE はモデル内部を複数の「エキスパート」に分け、トークンごとに一部しか使いません。総パラメータが 35B でも、1トークンあたりに実際に計算される量はずっと小さい。**「35B」を密なモデルと同列に語ると誤解します。**

入力処理は約 7,000 tok/s で頭打ち。TTFT は入力長にほぼ線形に伸びます。

もうひとつ、VRAM の空きが **316 トークンでも 25,669 トークンでも 3,284 MiB のまま 1MiB も動きませんでした**。LM Studio はロード時にコンテキスト分の KV キャッシュを確保しているようで、実行中に増えません。**長い入力で途中からVRAMが枯渇する心配は不要**で、可否はロード時点で決まります。

## 罠その1：41倍の嘘をついていた

最初の速度計測は、全部やり直しになりました。

各条件で同じプロンプトを5回投げていたのですが、結果がこうなっていました。

| 入力 | 1回目 TTFT | 2〜5回目 TTFT |
|---|---:|---:|
| 4,309 トークン | 0.579秒 | 0.058秒 |
| 8,569 トークン | 1.164秒 | 0.059秒 |
| 17,119 トークン | 2.422秒 | 0.059秒 |
| 25,669 トークン | 1.462秒 | 0.061秒 |

2回目以降が、**入力長に関係なく一律 0.058秒**。計算すると入力処理速度が **419,000 tok/s** になります。物理的にありえません。

**LM Studio のプロンプトキャッシュ**が効いていました。同じ入力を繰り返せば、2回目以降は処理済みの結果を使い回します。当然です。

さらに悪いことに、ダミー入力を共通の雛形から生成していたので、**24k のプロンプトが 16k のプロンプトの先頭部分をそのまま含んでいました**。条件をまたいでキャッシュが効き、24k の初回（1.462秒）が 16k の初回（2.422秒）より速いという逆転まで起きていました。

修正は、実行ごとにプロンプトの**先頭**を一意にすること。キャッシュは接頭辞の一致で効くので、末尾を変えても意味がありません。

### 転んだついでに測ってみた

せっかくなので、このキャッシュ効果自体を測りました。同じプロンプトを2回投げて cold / warm を比較します。

| 入力トークン | cold | warm | 高速化 |
|---:|---:|---:|---:|
| 1,093 | 0.220秒 | 0.057秒 | 3.9倍 |
| 4,306 | 0.639秒 | 0.057秒 | 11.2倍 |
| 17,115 | 2.470秒 | 0.060秒 | **41.0倍** |

warm 側は入力長によらず約0.06秒で一定なので、**入力が長いほど乖離が広がります**。17k トークンで41倍。

つまり、同じ入力を繰り返す評価スクリプトは、**実態の1/41の速さを「計測結果」として報告します**。しかもエラーは一切出ません。ただ速い数字が出るだけです。

なお、この罠が効くのは入力処理だけです。**生成速度と思考トークン量は影響を受けません**。

## 思考が答えを食い潰す

このモデルは reasoning モデルで、答える前に内部で「思考」を生成します。そして**思考も出力トークンの予算を消費します**。

「PONG とだけ答えて」と頼んだときの結果です。

```
finish_reason : "length"
content       : ""          ← 空
reasoning     : 146トークン
```

思考146トークンを使って、最終的な回答が出る前に予算切れ。**エラーにはなりません。**成功したレスポンスとして、中身が空で返ってきます。

`max_tokens` を変えて、空応答が出る割合を測りました（各30回）。

| max_tokens | 「PONGと答えて」 | 中程度の課題 |
|---:|---:|---:|
| 64 | 100% | 100% |
| 128 | 60% | 100% |
| 256 | **0%** | 100% |
| 512 | 0% | 60% |
| 1024 | 0% | **0%** |

**「PONGと答えて」に256トークンの予算が要ります。**

実用上ここが一番危険です。評価スクリプトがこれを検出せずに集計すると、**設定ミスが「不正解」として記録され、モデルの性能を過小評価します**。`finish_reason == "length"` かつ `content == ""` を失敗として弾く処理は必須です。

（ちなみに `finish_reason` が `"tool_calls"` のときも `content` は空になりますが、そちらは正常動作です。両方を空応答として弾くと、正常なツール呼び出しまで失敗扱いになります）

## 罠その2：予算の見積もりを二度外した

ここからが本題です。

上のデータから「難問なら 4096 あれば十分だろう」と見積もって、コード生成12問を回しました。結果がこれです。

```
t01_duration   easy    思考 4096 / 回答 0字   ← 最も簡単な問題
t06_flatten    medium  思考 4096 / 回答 0字
t10_diff       hard    思考 4095 / 回答 0字
t08_cycle      hard    思考 3852 / 回答 982字 (途中で打ち切り)
```

**12問中4問が思考だけで予算を使い切りました。**

空応答は採点で1点になります。その結果、平均スコアは 3.58。もし気づかずに公開していたら、「**35Bのコーディング特化モデルにコードを書かせたら5点満点で3.6点だった**」という、事実に基づいた完全な嘘の記事ができあがっていました。

予算を 16384 に上げて回し直すと、全12問が完走して平均 **4.75** になりました。**測っていたのはモデルの実力ではなく、私の設定ミスでした。**

### なぜ見誤ったのか

原因を調べて、想定していなかった事実が出ました。

| 出題時のラベル | 思考トークン中央値 | 範囲 |
|---|---:|---|
| **easy** | **8,937** | 7,689〜10,185 |
| medium | 3,033 | 2,351〜8,118 |
| hard | 3,510 | 1,246〜5,313 |

**最も簡単な問題が、最も多く思考していました。**

「ソート済みリスト2本をマージする」に **10,185トークン**。「`1h30m` を秒に変換する」に 7,689トークン。一方、最難関に分類した「スレッド競合を説明して直せ」は 1,246 で終わっています。

推測ですが、実装課題はエッジケースの列挙（空文字、未知の単位、空リスト、O(n)制約）で思考が膨張し、デバッグ課題は正解が一意なので早く収束するのだと思います。検証はしていません。

いずれにせよ実用上の結論は明確です。**問題の見た目の難しさから `max_tokens` を見積もる方法は成立しません。** コーディング用途なら 16384 を確保しておくのが安全です。

## で、実力はどうだったのか

前置きが長くなりました。計測結果です。

### ツール呼び出し：100%（60/60）

5種類のツールを定義し、20シナリオを各3回。

| 区分 | 精度 |
|---|---:|
| 呼ぶべき場面 | 100% |
| 呼ぶべきでない場面 | 100%（**誤検知 0%**） |

ツール選択ミス、引数ミス、誤検知が**1件もありません**。

含めた観点は、5種類からの適切な選択、引数の正確性、一般知識の質問でツールを呼ばないか、「テストファイルを列挙して、実行はするな」で `search_files` を選べるか、そして「そのうちチームに知らせないと」で**勝手に `send_email` を呼ばないか**。全部通りました。

### JSON スキーマ準拠：100%（60/60）

ネストしたオブジェクト、enum制約、配列、`additionalProperties: false` を含むスキーマで各30回。

**プロンプトで指示するだけで 100% 準拠**しました。`response_format` による強制は不要で、`` ```json `` フェンスで包む挙動も1件もなし。ローカルLLMでは「JSONと言ったのにマークダウンで返す」が定番の失敗ですが、皆無でした。

### 正直に書くと、この2つは天井に張り付いています

100%、100%。**これは私のテスト設計の識別力不足です。**

分かったのは「基本的なツール判断とJSON出力では破綻しない」という下限であって、**どこで壊れるかは測れていません**。満点を成果として誇るのではなく、天井に当たったこと自体を書くべきだと思っています。

### コード生成：4.75 / 5.00

12問（LRUキャッシュ、トークンバケット、リトライデコレータ、有向グラフの閉路検出、LCSベースのdiff、ストリーミング中央値、スレッド競合の説明、意図的に壊したコードの修正など）。

**12問中10問が満点。** これは素直に強いと思います。

## 審査員を2つ使った話

コード生成の採点は、Claude（claude-opus-5）と Gemini（gemini-3.8-flash）の**2つに独立してやらせました**。

理由は冗長化ではありません。**審査員が1つだと、その採点が妥当だったかを誰も検証できない**からです。読者は「Claude がそう言ったから」以上の根拠を得られません。

2つあると、一致率という検証可能な数字が出ます。

| 指標 | 値 |
|---|---:|
| 完全一致 | **91.7%**（11/12） |
| ±1以内 | 100% |
| 平均スコア差 | 0.08（Claude 4.75 / Gemini 4.83） |

### 両者が同じ誤りに独立に収束した

最低スコアだった問題が面白かったので書きます。

課題は「重複を含むソート済みリストで最初の出現位置を返す二分探索の欠陥を指摘し、**具体的な再現入力**を挙げ、修正版を示せ」。

Ornith は**欠陥の診断も修正コードも正しく**書きました。しかし再現入力を間違えました。`xs = [1, 2, 2, 3], target = 2` を挙げて「期待値は 0」と主張したのですが、`xs[0]` は 1 なので、2 の最初の出現は index 1 です。元のコードの返り値は正しい。

両審査員がこれを独立に指摘しました。

> **Claude**: 有効な再現入力は `[2, 2, 3]` のようなものになる。課題が具体的な再現入力を明示的に求めている以上、修正が妥当でもこれは実質的な欠陥である。

> **Gemini**: モデルは最初の出現が index 0 だと誤って主張しているが、`xs[0] == 1` である。

系統の異なる2社のモデルが、独立に、同じ微妙な誤りに収束しました。**採点が機能していることの証拠**であり、同時に **Ornith の弱点**でもあります。直し方は分かっているのに、自分が挙げた例を検算していない。

### 唯一の不一致も、雑音ではなかった

割れた1問（LRUキャッシュ、Claude 4 / Gemini 5）も、中を見ると理由がありました。

Claude は「`capacity=0` の退化ケースで、ダミーノードに対して削除を試みて KeyError になる。容量の検証もない」と指摘。Gemini はそこを検証していませんでした。

**どちらも誤りではなく、厳しさの差**です。不一致は平均で均さず、中身を見る価値があります。

### 事前に気にしていたバイアスについて

Ornith は **Gemma 4** の上に post-training されています。Gemma は Google 系です。つまり評価対象と Gemini の間には、Claude との間より近い血縁がありうる。LLM審査員の既知バイアスである「自分と同系統のモデルの出力を好む」が、**Gemini 側にだけ働く**可能性がありました。

結果は平均スコア差 0.08。系統的な甘さは観測されませんでした。ただし **12問で系統差を否定するには不十分**です。「この規模では検出されなかった」以上のことは書けません。

## まとめ：何が分かって、何が分からなかったか

**分かったこと**

- 4090 一枚 + 4bit量子化で、35B の MoE が **137.8 tok/s**。25kトークン入れても 127.2
- コード生成は **4.75/5.00**。12問中10問が2審査員から満点
- ツール呼び出しとJSON出力は、**この難易度では破綻しない**
- 弱点らしきものが1つ。**自分の挙げた例を検算しない**

**分からなかったこと**

- ツール呼び出しとJSON準拠が**どこで壊れるか**（天井に張り付いて識別できず）
- 難易度と思考量が逆相関する**理由**（観察のみ、未検証）
- 審査員の系統バイアスの**有無**（n=12では判定不能）
- ネイティブの 262,144 コンテキストでの挙動（24GBでは 32,768 が限界）

**測る側の教訓**

1. **プロンプトキャッシュを無効化しないと速度は測れない。** 17kトークンで41倍ずれる
2. **難易度から `max_tokens` を見積もれない。** 一番簡単な問題が一番思考した
3. **空応答を失敗として検出しないと、自分の設定ミスがモデルの点数になる**
4. **審査員は2つ用意する。** 一致率が無いと、採点が妥当だったか誰にも分からない

3番目が、この記事で一番書きたかったことです。平均3.58という数字は、私が予算を絞りすぎただけでした。エラーは出ませんし、レスポンスは正常に返ってきます。**気づく手がかりは「思考トークン数が上限に張り付いている」ことだけ**でした。
