# 1. Git / GitHub

**リポジトリ (repository)**
ファイルとその変更履歴をまとめて管理する単位。手元の作業ディレクトリ（`.git` を含むフォルダ）がローカルリポジトリ、GitHub 上のものがリモートリポジトリにあたる。

**`git init`**
ディレクトリをGitリポジトリとして初期化するコマンド。`.git` という隠しディレクトリが作られ、そこに履歴が全部入る。

**ブランチ (branch) / `main` / `master`**
変更履歴の枝分かれの単位。歴史的に既定名は `master` だったが、現在のGitHubの慣習は `main`。`git init -b main` の `-b` で初期ブランチ名を明示的に指定している。

**コミット (commit)**
変更を履歴に確定させる操作、およびその1単位。各コミットには `e54774b` のようなハッシュIDが付く。

**リモート (remote) / `origin`**
ネットワーク上にある対応リポジトリ。`origin` は「主たるリモート」に付ける慣習的な名前で、特別な意味を持つ予約語ではない単なるラベル。

**push / 追跡ブランチ (tracking branch)**
push はローカルのコミットをリモートに送る操作。追跡ブランチはローカルブランチとリモートブランチの対応付けで、これが設定済みなら `git push` だけで送り先が決まる。

**`.gitignore`**
Gitの管理対象から除外するファイルのパターンを書くファイル。**APIキーを含む `.env` を除外するのが最重要**。一度コミットしてしまうと履歴に残り、後から消すのは面倒なので最初に設定する。

**`.env` / `.env.example`**
`.env` は環境変数（APIキーなど秘密情報）を書くファイルで、Git管理外。`.env.example` は「何のキーが必要か」だけを示す雛形で、こちらは値を空にしてコミットする。

**`gh` CLI**
GitHubをコマンドラインから操作する公式ツール。リポジトリ作成やPR操作ができる。

**`gh auth login` / スコープ (scope)**
GitHubへの認証。スコープは発行されたトークンに許可された権限の範囲。このプロジェクトでは `gist`, `read:org`, `repo`, `workflow` が付与されている（`repo` がリポジトリ読み書きの権限）。

**private / public**
リポジトリの公開設定。APIキーを扱う実験リポジトリは private が安全。後から変更可能。

**`git status -sb`**
状態を短い形式（`-s`）でブランチ情報付き（`-b`）で表示する。`## main...origin/main` だけが出ればローカルとリモートが完全に同期している状態。

# 2. LM Studio と推論基盤

**ローカルLLM**
クラウドAPIではなく手元のマシンで動かす大規模言語モデル。従量課金が無くデータが外部に出ない代わりに、マシン性能が上限になる。

**LM Studio**
ローカルLLMをGUIで管理・実行できるアプリケーション。内部で llama.cpp を使い、OpenAI互換のHTTPサーバー機能を持つ。

**llama.cpp**
C/C++で書かれたLLM推論エンジン。GGUF形式のモデルを動かす事実上の標準。LM Studio はこれをラップしている。この文書に出てくる低レベルなパラメータ（`n_ctx` など）は概ね llama.cpp 由来。

**GGUF**
llama.cpp が使うモデルファイル形式。モデルの重みに加えて、トークナイザやチャットテンプレートなどのメタデータも1ファイルに含む。

メタデータはファイル先頭に格納されているため、**Pythonで数十行のパーサを書けば全部読める**（重み本体を読み込む必要はない）。チャットテンプレートの検証に有用。

✅ 本プロジェクトの GGUF から読み取った主な値:

```
general.architecture      = qwen35moe
general.size_label        = 35B
general.license           = mit
general.base_model.0.name = Ornith 1.0 35B
qwen35moe.context_length  = 262144
tokenizer.chat_template   = (7,686 bytes)
```

⚠️ **メタデータの不備を発見。** `general.name` と `general.basename` が **`Ornith-1.0-9B`** になっている（実際は35B）。`size_label` と `base_model` は正しく35Bを指しているので、**配布時のラベル付けミス**と考えられる。推論動作には影響しないが、**GGUFのメタデータを無条件に信用してはいけない実例**。記事に構成情報を書く際は、複数のフィールドを突き合わせて確認すること。

**エンドポイント (endpoint) / ポート (port)**
エンドポイントはAPIの接続先URL。ポートは1台のマシン内で通信の入口を区別する番号。このプロジェクトでは `http://127.0.0.1:1235`（`127.0.0.1` は自マシンを指すアドレス。LM Studioの既定ポートは1234だが、ここでは1235を使用）。

**OpenAI互換API**
OpenAIのAPIと同じリクエスト／レスポンス形式を実装したAPI。これにより、OpenAI向けに書かれたクライアントライブラリの接続先を変えるだけでローカルLLMが使える。

**`/v1/models`**
利用可能なモデル一覧を返すエンドポイント。✅ 3件（ornith / gemma / nomic-embed）を確認。

**`/v1/chat/completions`**
チャット形式で推論を実行する中心的なエンドポイント。`messages` に会話履歴を配列で渡す。

**`/v1/embeddings`**
テキストを数値ベクトル（埋め込み）に変換するエンドポイント。✅ 768次元のベクトルを取得できた。

**`/api/v0/models`**
LM Studio独自のAPI。OpenAI互換の `/v1/models` では見えない**量子化形式・アーキテクチャ・コンテキスト長・ロード状態**が取得できる。記事に載せる構成情報はここから取るのが確実。

**`lms` CLI**
LM Studio付属のコマンドラインツール。主なサブコマンド:

| コマンド | 用途 |
|---|---|
| `lms ps` | ロード中モデルの一覧と設定（`--json` で詳細） |
| `lms ls` | ダウンロード済みモデルの一覧（**正しいモデルキーはここで確認する**） |
| `lms load` / `lms unload` | モデルのロード / アンロード |
| `lms server status` | サーバーの稼働状態とポート |
| `lms log stream` | 実際に整形されたプロンプトを覗く（テンプレート確認用） |

**ロード時パラメータ（`lms load` のオプション）**
以下は**モデルをロードする瞬間にしか指定できない**設定。変更には再ロードが必要で、⚠️ **APIからは変更できない**（後述の「LM Studio APIで出来ること・出来ないこと」を参照）。

| オプション | 内容 |
|---|---|
| `--parallel <n>` | 同時実行可能なリクエスト数 |
| `-c, --context-length <n>` | コンテキスト長 |
| `--gpu <ratio>` | GPUオフロード率。`max` で全レイヤー、`off` で無効、0〜1で割合指定 |
| `--ttl <秒>` | 自動アンロードまでの秒数 |
| `--identifier <名前>` | API から参照する際の識別子 |
| `--estimate-only` | **ロードせずに必要リソースを試算する**（設定変更前の検討に有用） |
| `--speculative-draft-*` | 投機的デコード関連（第8章参照） |

**`--estimate-only`（リソース試算）**
実際にロードせずメモリ必要量を見積もる。✅ ornith / ctx 32768 で **18.23 GiB** と表示された。⚠️ ただし LM Studio 自身が `Confidence: LOW`（推定の信頼度が低い）と併記するため、この数値は目安として扱う。

**LM Studio API で出来ること・出来ないこと**
API（`/v1/...` と `/api/v0/...`）で出来るのは**推論の実行とモデル情報の取得まで**。モデルのロード設定（`parallel`、コンテキスト長、GPUオフロード等）は変更できない。変更手段は `lms` CLI / GUI / SDK の3つ。

⚠️ **重要な落とし穴 — エラーの返り方が2通りある。**

**① 存在しないエンドポイント → HTTP 200 + ボディに `error`**

```
GET /api/v0/config             → 200  {"error":"Unexpected endpoint or method."}
GET /api/v0/bogus-nonexistent  → 200  {"error":"Unexpected endpoint or method."}
```

**② コンテキスト超過 → HTTP 400（例外）**

```
POST /api/v0/chat/completions  → 400  exceed_context_size_error
```

つまり **ステータスコードだけでも、ボディだけでも不十分**。両方を扱う必要がある。

✅ 実際にこれで一度スクリプトが落ちた。Python の `urllib` は 4xx で例外を投げるため、ボディの `error` キーを見る前に処理が中断する。**HTTPError を捕捉して本文を読み直す**実装にすること。

```python
try:
    with urllib.request.urlopen(req) as resp:
        return json.loads(resp.read())
except urllib.error.HTTPError as e:
    return json.loads(e.read())   # 本文にエラー詳細が入っている
```

**サーバー側の計測値 — `/api/v0` を使う理由**
OpenAI互換の `/v1` では `stats` が空だが、✅ **`/api/v0/chat/completions` は計測済みの値を返す**:

```json
"stats": {
  "tokens_per_second": 148.2,
  "time_to_first_token": 0.2099,
  "generation_time": 1.5594,
  "stop_reason": "eosFound"
}
```

**TTFT をクライアント側でストリーミング計時する必要がない**ため、計測スクリプトは `/api/v0` を使う方が正確かつ簡単。`model_info`（arch / quant / context_length）も同時に返るので、構成情報の記録にも使える。

**TTL (Time To Live) / 自動アンロード**
モデルを最後に使ってから何分でメモリから降ろすかの設定。`lms ps --json` の `ttlMs`（ミリ秒）。✅ 埋め込みモデルは1時間、ornith は `null`（自動アンロードしない）。**計測中にアンロードされるとロード時間が混入して数値が汚れる**ので、評価前に確認する。

**JITロード (Just-In-Time loading)**
リクエストが来た時点でモデルを読み込む方式。初回リクエストだけ極端に遅くなる。

**`parallel` / スロット (slot)**
同時に処理できるリクエストの本数。**ロード時パラメータ**なので、変更にはモデルの再ロードが必要（APIからは変更できない。後述）。

llama.cpp の `--parallel` はコンテキストをスロット数で分割する実装（32768 ÷ 4 = 8192）だが、✅ **LM Studio では分割されないことを実測で確認**。`parallel: 4`・context 32768 の状態で、単一リクエストが `prompt_tokens: 22425` を処理できた。

さらに ✅ `--estimate-only` による試算でも **parallel 1 と 4 でメモリ推定値は同一（18.23 GiB）**。LM Studio は parallel 数に関わらず `n_ctx` 分のKVキャッシュを1つ確保し、`parallel` はその中での同時処理本数を制御しているだけと見られる。

→ **評価のために `parallel` を 1 に下げる必要はない。** 「並列数を減らせばVRAMが浮く」は llama.cpp の挙動からの類推であり、LM Studio には当てはまらなかった。評価スクリプトを逐次実行で書く限り、スロット競合も発生しない。⚠️ 4本同時実行時の挙動は未検証。

**curl**
コマンドラインからHTTPリクエストを送るツール。この文書で使った主なオプション: `-s`（進捗非表示）、`-m`（タイムアウト秒）、`-d` / `--data-binary`（送信データ）、`-w`（HTTPステータスや所要時間の書式出力）。

# 3. モデルの性質

**パラメータ数 (35B)**
モデルの重みの個数。B = billion（10億）。大きいほど高性能な傾向だが、必要メモリも増える。

**MoE (Mixture of Experts / 専門家混合)**
モデル内部を複数の「エキスパート」に分け、**トークンごとに一部だけを使う**構造。総パラメータ数が大きくても、1トークンあたりに実際に計算される**アクティブパラメータ**はずっと少ないため高速。✅ ornith が35Bクラスながら約60 tok/s 出たのはこれで説明がつく。**「35B」を密（dense）なモデルと同列に語ると誤解を招く**ので、記事では MoE である点を明記する。

**アクティブパラメータ (active parameters)**
MoEで1トークンの生成時に実際に使われるパラメータ数。速度はこちらに比例し、必要メモリは総パラメータ数に比例する。⚠️ ornith の具体的なアクティブパラメータ数は未確認。

**アーキテクチャ (architecture)**
モデルの構造の型。`lms ps --json` が報告する `architecture` は llama.cpp が認識した型名で、✅ ornith は `qwen35moe`（Qwen系のMoE構造）。

**VLM (Vision Language Model) / マルチモーダル**
テキストに加えて**画像も入力できる**モデル。✅ ornith は `vision: true`。画像理解の評価軸が丸ごと使える。

**reasoning モデル（推論モデル）**
答える前に内部で「思考」の過程を生成するモデル。思考部分と最終回答が分離して返る。✅ ornith はこのタイプ。

**tool use / function calling（ツール利用 / 関数呼び出し）**
モデルが外部の関数やAPIを「呼ぶべきだ」と判断し、関数名と引数を構造化して出力する能力。

Ornith はモデル本体が `<tool_call>` 形式のブロックを出力し、サーバー側の**ツールコールパーサ**がそれを OpenAI 形式の `tool_calls` に変換する。vLLM では `--tool-call-parser qwen3_xml` を明示指定する必要がある。

✅ **LM Studio では設定不要で正しく動作することを実測で確認**（`get_weather` ツールを定義して「パリの天気は?」と質問）:

```json
"finish_reason": "tool_calls",
"tool_calls": [{"type":"function","id":"...",
  "function":{"name":"get_weather","arguments":"{\"city\":\"Paris\"}"}}]
```

関数名・引数ともに正しく構造化されていた。**エージェント評価の土台が動くことが確認できた**という点で重要。

**埋め込みモデル (embedding model) / 次元 (dimensions)**
テキストを意味を表す数値ベクトルに変換する専用モデル。次元はそのベクトルの長さ。✅ nomic-embed-text-v1.5 は768次元。文書検索やRAGの土台になる。

**publisher / unsloth**
`lms ps` が報告する配布元。⚠️ **unsloth はGGUF形式に量子化して再配布した主体であり、モデル本体の開発元ではない。** 記事で開発元として書かないこと。

**モデルカード (model card)**
モデル配布ページに置かれる説明文書。学習データ、ライセンス、**推奨サンプリング設定**、ベンチマーク結果などが書かれる。評価を始める前に必ず読む。

# 4. 量子化

**量子化 (quantization)**
モデルの重みを低いビット幅に丸めてファイルサイズとメモリ使用量を削減する技術。**同じモデルでも量子化の強さで性能が別物になる**ため、評価記事では量子化形式の明記が必須。

**F16 / FP16**
16bit浮動小数点。量子化していない（またはほぼ素の）状態。品質は最良、メモリ消費も最大。

**Q4_K_M / Q8_0**
llama.cpp の量子化形式の命名。`Q` の後ろの数字がおおよそのビット幅、後半は手法の種別を表す。数字が大きいほど高品質・大サイズ。✅ 同じ環境にある gemma と nomic-embed は Q4_K_M。

**IQ4_XS**
llama.cpp の **i-quant系** 4bit量子化のひとつ。従来の `Q4` 系より小さいサイズで品質を保つことを狙った方式。✅ ornith はこれ。

**UD (Unsloth Dynamic)**
Unsloth による量子化手法。**レイヤーごとにビット幅を変える**（重要な層は高い精度で残す）点が均一量子化と異なる。✅ ファイル名の `UD-IQ4_XS` がこれを示す。記事では「均一な4bitではない」と一言添えると正確。

**量子化と品質のトレードオフ**
強く量子化するほど省メモリ・高速だが精度は落ちる。⚠️ **どの程度落ちるかはモデル依存で、一般論では語れない。** 評価するなら同一モデルの複数の量子化を比較する必要がある。

# 5. トークンとコンテキスト

**トークン (token) / トークナイザ (tokenizer)**
モデルが扱うテキストの最小単位。単語より細かく文字より粗い。トークナイザがテキストをトークン列に分割する。**日本語は英語より1文字あたりのトークン消費が多い**傾向があり、コンテキストの計算に効いてくる。

**コンテキスト長 (context length) / `n_ctx`**
モデルが一度に扱えるトークン数の上限。入力と出力の**合計**に対する制限である点が重要。

**`max_context_length` / `loaded_context_length`**
前者はモデルが対応可能な最大値、後者は**現在のロード設定で実際に確保されている値**。✅ ornith は max 262,144 に対しロードは 32,768。**評価で意味を持つのは後者**なので、記事にはロード値を書く。

**KVキャッシュ (KV cache)**
生成済みトークンの中間計算結果を保持しておく領域。これがあるおかげで毎トークン全部を計算し直さずに済む。**コンテキスト長に比例してメモリを消費する**ため、長文対応の主なコストはここに出る。

⚠️ **重要な訂正。** 当初この文書には「KVキャッシュは使うほど伸びる」と書いていたが、✅ **LM Studio では誤り**。Phase 1 で入力 316 トークンから 25,669 トークンまで変化させても、**VRAM空きは 3,284 MiB から1 MiBも動かなかった**。ロード時に `loaded_context_length` 分を先に確保する方式と考えられる。

実用上の意味：**長い入力を流しても実行中にVRAMが枯渇することはない**。VRAMの可否はロード時点で決まる。

**プロンプトキャッシュ / プレフィックスキャッシュ (prompt cache / prefix caching)**
直前までに処理した入力の KV を保持し、**次の入力の接頭辞が一致する範囲を再計算せずに使い回す**仕組み。LM Studio では既定で有効。

⚠️ **評価における最大の落とし穴。** 同じ入力を N 回繰り返すと2回目以降がキャッシュヒットし、TTFT が入力処理の実態を全く反映しなくなる。

✅ 実測した影響（同一プロンプトの1回目と2回目）:

| 入力トークン | cold TTFT | warm TTFT | 高速化 |
|---:|---:|---:|---:|
| 1,093 | 0.220s | 0.057s | **3.9倍** |
| 4,306 | 0.639s | 0.057s | **11.2倍** |
| 17,115 | 2.470s | 0.060s | **41.0倍** |

warm 側は入力長によらず一定（約0.06秒）で、**入力が長いほど乖離が大きくなる**。

**対策**：prefill を測るなら**実行ごとにプロンプトの先頭を一意にする**（末尾を変えても無意味。キャッシュは接頭辞で一致するため）。条件をまたいだ共有にも注意 — 共通の雛形から生成したダミー入力は、長い条件が短い条件の接頭辞を含んでしまう。

なお **decode 速度と思考トークン量はキャッシュの影響を受けない**（キャッシュが効くのは入力処理だけ）。

**KVキャッシュ量子化**
KVキャッシュ自体を量子化（例: F16 → Q8_0）してメモリを削減する設定。長いコンテキストを確保したいがVRAMが足りない場合の主要なレバー。品質への影響は重みの量子化より小さいとされるが、⚠️ ゼロではない。

**Flash Attention**
Attention計算を効率化する実装。メモリ使用量を減らし高速化する。基本的に有効化して不利になる場面は少ない。

**コンテキスト超過 (context overflow)**
入力がコンテキスト長を超えた状態。✅ **LM Studio の API は黙って切り詰めず、HTTP 400 で明示的に失敗する**ことを確認:

```json
{"code":400,"type":"exceed_context_size_error",
 "message":"request (44825 tokens) exceeds the available context size (32768 tokens)",
 "n_prompt_tokens":44825,"n_ctx":32768}
```

評価用途では**静かな切り詰めより明示的なエラーの方が望ましい**（原因不明の精度低下にならないため）。

**`usage` — トークン消費の内訳**
APIレスポンスに含まれる集計。

| フィールド | 意味 |
|---|---|
| `prompt_tokens` | 入力に消費したトークン数 |
| `completion_tokens` | 出力に消費したトークン数（思考を含む） |
| `reasoning_tokens` | そのうち**思考**に使われた分 |
| `total_tokens` | 合計 |

✅ ornith は「PONGとだけ答えて」に対し `reasoning_tokens: 146`、最終回答はわずか5トークンだった。
⚠️ 埋め込みエンドポイントは `prompt_tokens: 0` を返すため、トークン計測には使えない。

# 6. 推論パラメータ（サンプリング）

生成のたびに「次の1トークン」を候補の確率分布から選ぶ。その選び方を制御するのがサンプリングパラメータ。**評価では全部を固定し、記事に明記する。**

**`temperature`（温度）**
出力のランダム性。低いほど確定的で保守的、高いほど多様で創造的になる。

**greedy decoding（貪欲デコード / `temperature: 0`）**
毎回最も確率の高いトークンを選ぶ方式。再現性が高い一方、⚠️ **モデルによっては同じ語句を繰り返すループに陥る**ことが知られている。

**Ornith の推奨サンプリング設定（モデルカード確認済み）**

Quickstart に記載された推奨値:

| パラメータ | 推奨値 |
|---|---|
| `do_sample` | `True`（＝greedy decoding を使わない） |
| `temperature` | **0.6** |
| `top_p` | **0.95** |
| `top_k` | **20** |
| `max_tokens` | 例では 1024〜2048 |

⚠️ **初期の計測（PONGテスト等）はすべて `temperature: 0` で取得したもので、推奨から外れている。** 速度・品質の数値は上記の設定で取り直す必要がある。

⚠️ **さらに注意 — 公称ベンチマークは推奨値と違う設定で取られている。** モデルカードの脚注によると、実際の評価は概ね以下:

| ベンチマーク | 設定 |
|---|---|
| Terminal-Bench 2.1 | temp **1.0** / top_p 1.0 / 128K context |
| SWE-bench 各種 | temp **1.0** / top_p 0.95 / 256K context |
| NL2Repo | temp **1.0** / top_p 1.0 / 400K context |
| ClawEval | temp **0.6** / 256K context |

つまり **Quickstart推奨(0.6) と 公称スコアの再現条件(1.0) が一致しない**。記事で「公称値と比べる」なら 1.0、「推奨通りに使う」なら 0.6 と、**目的に応じて選び、どちらを使ったか明記する**必要がある。

**`top_p`（核サンプリング / nucleus sampling）**
確率の高い順に累積確率が `top_p` に達するまでの候補だけを残す。0.95 なら上位95%相当の候補から選ぶ。

**`top_k`**
確率上位 k 個の候補だけを残す。`top_p` と併用されることが多い。

**`min_p`**
最有力候補の確率に対する相対的な閾値で候補を足切りする方式。`top_p` より安定するとされる。

**`repeat_penalty`（繰り返しペナルティ）**
既出トークンの確率を下げて繰り返しを抑制する。⚠️ **reasoning モデルでは思考が長く同じ語が自然に何度も出るため、強くかけると思考を壊す恐れがある。** 安易に上げない。

**`seed`（乱数シード）**
乱数の初期値。固定すれば再現性が上がるが、⚠️ **GPU上の並列演算は加算順序が変わりうるため、seed固定でも完全な決定論にはならない。** 同じ条件でN回試行し、ばらつきを報告するのが誠実。

**`max_tokens`**
生成する最大トークン数。⚠️ **reasoning モデルでは最重要の落とし穴。** 思考もこの枠を消費するため、小さすぎると思考だけで使い切り、最終回答が空になる。

✅ このプロジェクトで実際に2回踏んだ:

- `max_tokens: 32` → `content: ""`, `finish_reason: "length"`
- `max_tokens: 200`（長文入力時） → 同様に空

✅ **Phase 2 で必要な予算を定量化した**（空応答が発生した割合、N=5）:

| max_tokens | 自明な課題 | 中程度の課題 |
|---:|---:|---:|
| 64 | 100% | 100% |
| 128 | 60% | 100% |
| 256 | **0%** | 100% |
| 512 | 0% | 60% |
| 1024 | 0% | **0%** |
| 2048 | 0% | 0% |

⚠️ **さらに、2048 でも難問には不足する。** 難易度ラダーの検証で、**難問9回中6回が上限2048に到達**し、うち3回は最終回答が空になった（中程度でも9回中2回が到達）。

| 難易度 | 思考トークン中央値 | 範囲 |
|---|---:|---|
| 自明 | 142 | 106〜196 |
| 簡単 | 410 | 93〜523 |
| 中程度 | 1,403 | 444〜1,935 |
| **難問** | **1,940** | 1,132〜2,048（**上限張り付き**） |

⚠️⚠️ **さらに訂正: 4096 でも足りなかった。** 上の表から「コーディング用途は 4096 以上」と推定したが、Phase 3 で実際にコード生成させたところ **12問中4問が 4096 の上限に達した**（3問は回答が完全に空、1問は途中で切れた）。空になった1問はこのセットで最も簡単な課題だった。

✅ **難易度ラベルから必要予算を見積もる方法は成立しない。** Phase 3 の実測:

| 出題時のラベル | 思考トークン中央値 | 範囲 |
|---|---:|---|
| **easy** | **8,937** | 7,689〜10,185 |
| medium | 3,033 | 2,351〜8,118 |
| hard | 3,510 | 1,246〜5,313 |

**最も簡単な課題が最も多く思考した**（人間から見た難易度と逆相関）。実装課題はエッジケースの列挙で思考が膨張し、デバッグ課題は正解が一意なので早く収束する、というのが推測される理由（⚠️未検証）。

→ **コーディング用途では 16384 を割り当てる。** 本計測での最大は 10,185 トークン。通常の短い応答なら 2048 で足りるが、**課題の見た目の難しさを予算の根拠にしてはいけない**。

評価スクリプトには `finish_reason == "length"` かつ `content == ""` を**失敗として検出する処理**を必ず入れる（`"tool_calls"` は除外）。入れないと設定ミスが「不正解」として集計され、モデルの性能を過小評価する。実際に Phase 3 の初回実行では、この予算不足がそのまま平均スコアに化けた（3.58 → 予算を上げると 4.75）。

**`finish_reason`（終了理由）**
生成が止まった理由。

| 値 | 意味 |
|---|---|
| `"stop"` | 正常終了（モデルが自ら終えた） |
| `"length"` | `max_tokens` に到達して打ち切られた |
| `"tool_calls"` | ✅ ツール呼び出しを要求して停止（`tool_calls` に中身が入る） |

⚠️ **`content` が空になるケースは2種類あり、区別が必要。**

| finish_reason | content | 意味 | 扱い |
|---|---|---|---|
| `"length"` | `""` | `max_tokens` 不足の**設定ミス** | **失敗として弾く** |
| `"tool_calls"` | `""` | ツール呼び出し。**正常動作** | 正常として扱う |

評価スクリプトで空応答を検出する際、`finish_reason` を見ずに `content == ""` だけで弾くと**正常なツール呼び出しまで失敗扱いになる**ので注意。

**`stream`（ストリーミング）**
生成結果を1トークンずつ逐次返す方式。TTFT の計測にはこれが必要。

**チャットテンプレート (chat template)**
`messages` の配列を、そのモデルが学習時に見た形式の1本のテキストに整形する規則。GGUFのメタデータに含まれ通常は自動適用される。**間違うと出力品質が大きく劣化する。** 疑わしい時は `lms log stream` で実際の整形結果を確認する。

**Ornith 固有の注意点。** モデルカードの評価脚注に、**「学習時と推論時の整合を取るため Qwen のチャットテンプレートを修正した」**旨が2箇所で明記されている（修正版 `chat_template.jinja` へのリンクあり）。つまり素の Qwen テンプレートはこのモデルにとって不正解。

### ✅ 検証結果: 使用中のGGUFのテンプレートは適切

2つの方法で確認した。

**① 実際の整形結果（`lms log stream`）**

```
<|im_start|>system
# Tools

You have access to the following functions:

<tools>
{"type":"function","function":{"name":"marker_tool", ...}}
</tools>

If you choose to call a function ONLY reply in the following format with NO suffix:

<tool_call>
<function=example_function_name>
<parameter=example_parameter_1>
...
</IMPORTANT>

（システムプロンプト本文）<|im_end|>
<|im_start|>user
（ユーザー入力）<|im_end|>
<|im_start|>assistant
<think>
```

- ChatML 形式（`<|im_start|>` / `<|im_end|>`）で正しく整形されている
- ツール定義はシステムメッセージ内に注入され、**公式テンプレートと一字一句一致**
- アシスタントターンが `<think>` で開始される（reasoning モデルとして正しい）

**② GGUFメタデータから抽出したテンプレート本体**

`tokenizer.chat_template` を直接読み出し（7,686 bytes）、公式2種と比較した。

| 比較対象 | 差分行数 | reasoning の履歴保持 |
|---|---|---|
| モデルカード参照版（397B） | 46行 | **除去する**（GGUFと同じ挙動） |
| 35B リポジトリの公式版 | 50行 | **保持する**（GGUFと挙動が異なる） |

→ **GGUF埋め込みテンプレートはモデルカード参照版（＝修正版）の系統**であり、カードが警告していた修正が**反映されている**。末尾に `{#- Unsloth fixes - developer role, tool calling #}` というコメントがあり、unsloth が独自の修正を加えたものと分かる。

**unsloth による追加変更点**

1. `developer` ロールに対応し、先頭2件までの system/developer メッセージを結合
2. 例外送出を3箇所削除（ユーザークエリ無し・system位置不正・不明ロール）→ より寛容
3. ツール引数の直列化を修正（`is defined` → `is mapping`）
4. `preserve_thinking` フラグを追加（有効にすると履歴の思考を保持）

**⚠️ 唯一の相違点: 履歴の思考ブロックの扱い**

✅ マルチターンで実測したところ、**過去のアシスタントターンの `<think>` は履歴から除去される**。

```
（送信）assistant: "<think>PRIOR_REASONING</think>PRIOR_ANSWER"
（整形）<|im_start|>assistant
        PRIOR_ANSWER<|im_end|>     ← 思考が消えている
```

これはモデルカード参照版と同じ挙動だが、**35Bリポジトリ自身のテンプレートとは異なる**（そちらは保持する）。Qwen3系では除去が標準的な作法であり、カードがリンクした修正版もそうしているため、**現状のままで問題ないと判断できる**。⚠️ ただしマルチターンのエージェント評価を行う場合、この挙動の違いが結果に影響しうる点は記録しておく。

**システムプロンプト (system prompt)**
モデルの役割や制約を指示する、会話の先頭に置くメッセージ。評価では全条件で揃えるか、意図的に変えるなら記録する。

# 7. メモリとハードウェア

**VRAM (Video RAM)**
GPU搭載メモリ。**モデルの重み + KVキャッシュ**がここに載る。ローカルLLMで動かせるモデルサイズを決める最大の制約。

**GPUオフロード (GPU offload) / レイヤー (layer)**
モデルの各層をGPUに載せる設定。**1層でもCPU側に残ると速度が桁で落ちる**。特にMoEは影響が大きい。全層がGPUに載っているかは評価前に確認する。

CLIから明示指定できる（GUIでの操作は必須ではない）:

```bash
lms load ornith-1.0-35b --gpu max    # 全レイヤーをGPUへ
```

`--gpu` を省略すると LM Studio が自動で最適な比率を決める。⚠️ **自動判定がVRAMの余裕を見て一部をCPUに残す可能性がある**ため、速度を計測するなら明示する方が確実。

**ヘッドルーム (headroom)**
VRAMの空き容量。✅ 不要アプリを閉じた状態で **3,284 MiB**（24,564中 21,280使用）。

✅ **この値は入力長によらず一定**（Phase 1 で 316〜25,669 トークンを通して不変）。KVキャッシュがロード時に確保済みのため、**実行中に目減りしない**。したがってヘッドルームは「ロード設定が載るかどうか」の判断材料であって、実行時の枯渇リスクを表すものではない。

**コンテキスト長を増やす余地はほぼ無い**（増やすならKVキャッシュ量子化とセット）。なお `parallel` はメモリに影響しないため、この制約とは無関係。

参考：不要アプリ（Chrome 18プロセス等）を閉じることで 2,532 → 3,284 MiB と **約750 MiB 回収**できた。dwm（デスクトップ描画）が単体で約390 MiB 使うが、これは停止できない。

**sysmem fallback（システムメモリフォールバック）**
⚠️ **Windows + NVIDIA 固有の罠。** VRAMが不足すると、ドライバがエラーを出さずにシステムRAMへ退避し、**速度だけが静かに激減する**。ベンチマーク中に起きると、原因不明の遅い数値を掴まされることになる。

対策: NVIDIAコントロールパネルの「CUDA - システムメモリフォールバックポリシー」を **「システムメモリフォールバックを優先しない」** に設定すると、溢れた際に**エラーで落ちる**ようになる。評価環境では、静かな劣化より明示的な失敗の方が扱いやすい。

**CUDA**
NVIDIA GPU上で汎用計算を行うための基盤。llama.cpp のGPU実行はこれを利用する。

**このプロジェクトのハードウェア**
RTX 4090（VRAM 24GB）/ Intel i9-14900KF / RAM 64GB。⚠️ **性能数値はハードウェア構成とセットでなければ意味を持たない**ので、記事には必ず併記する。

# 8. 性能指標

**tok/s（トークン毎秒 / tokens per second）**
1秒あたりの生成トークン数。ローカルLLMの体感速度を最も直接に表す。

✅ **実測 137.8 tok/s**（入力316トークン時、N=5の中央値）。⚠️ この文書には当初「約60 tok/s」と書いていたが、**入力処理時間を含めた単一サンプルの粗い値で、実態と大きく異なっていた**。

自前で計算する場合は `completion_tokens ÷ 生成時間` だが、**LM Studio の `/api/v0` はサーバー側の計測値を `stats.tokens_per_second` で返す**ので、そちらを使う方が正確（後述）。

**TTFT (Time To First Token)**
リクエスト送信から最初の1トークンが返るまでの時間。「反応の速さ」の体感を決める。`stream: true` にして最初のチャンク到達時刻を測る。

**prefill（プロンプト処理） / decode（生成）**
prefill は入力全体を読み込む段階、decode は1トークンずつ生成する段階。**両者は速度特性が全く異なる**（prefill は並列化が効いて高速、decode は逐次処理）。⚠️ **合算した数値は入力長で変動して比較不能になるため、分けて測る。**

**ロード時間 (load time)**
モデルをディスクからメモリに読み込む時間。✅ gemma の初回リクエストが9.3秒かかり、2回目以降は高速だった。

**ウォームアップ (warm-up)**
本計測の前に、捨てるための実行を数回行うこと。ロード時間やキャッシュ未整備の影響を計測から除くために必須。

**投機的デコード (speculative decoding)**
小さく速い「ドラフトモデル」に次のトークンを先読みさせ、本命モデルはそれをまとめて検証するだけにすることで高速化する手法。検証で不一致なら破棄されるため、**出力品質を変えずに速度だけを上げられる**のが原理上の利点。

`lms load` のオプションで指定する:

| オプション | 内容 |
|---|---|
| `--speculative-draft-mtp` | モデル内蔵の MTP (Multi-Token Prediction) を使う方式 |
| `--speculative-draft-simple` | 別モデルをドラフトに使う方式 |
| `--speculative-draft-model <model>` | 上記で使うドラフトモデルの指定 |
| `--speculative-draft-max-tokens <n>` | 1ステップあたりの先読みトークン数の上限 |

⚠️ **ornith が MTP に対応しているかは未確認。** 有効/無効でロードして tok/s を比較すれば分かる。**記事の題材として面白い**（同じモデル・同じ品質で速度だけが変わる比較になる）。

# 9. 評価手法

## 9.1 定量ベンチマーク

**ベンチマーク (benchmark)**
標準化された問題集でモデルを採点する手法。他モデルとの比較がしやすい反面、実行に時間がかかる。

| 名称 | 測る対象 |
|---|---|
| MMLU / MMLU-Pro | 多分野の一般知識・理解 |
| GPQA | 専門家レベルの難問 |
| GSM8K | 小学校レベルの算数の文章題 |

**ベンチマーク汚染 (contamination)**

## 9.2 LLM-as-a-judge

**LLM-as-a-judge**
モデルの出力を人間ではなく別の高性能LLMに採点させる手法。人手評価より高速・安価で、自動ベンチより柔軟な評価ができる。このプロジェクトでは Claude を審査員に使う想定。

**ペアワイズ比較 (pairwise comparison)**
2つの出力を並べてどちらが良いか判定させる方式。絶対評価より判断が安定しやすい。

**ルーブリック採点 (rubric grading)**
評価基準を明文化し、単一の出力を点数（例: 1〜5）で採点する方式。

**MT-Bench / Arena-Hard / AlpacaEval**
LLM-as-a-judge を用いた代表的な評価セット。マルチターン対話や難問への応答品質を測る。

**審査員LLMの既知のバイアス**

| バイアス | 内容 | 対策 |
|---|---|---|
| 位置バイアス | 先に提示された方を高く評価しがち | A/Bの順序を入れ替えて2回判定し、一致時のみ採用 |
| 冗長性バイアス | 長い回答を高く評価しがち | ルーブリックに簡潔さの項目を明記 |
| 自己強化バイアス | 自分と同系統のモデルの出力を好む | 審査員と被験モデルの系統を分ける |

**Elo レーティング**
対戦結果の集積から相対的な強さを算出する方式。多数のペアワイズ比較結果を1つの序列にまとめるのに使われる。

## 9.3 タスク特化の評価

**Needle in a Haystack（干し草の山の中の針）**
長文の中に特定の情報を埋め込み、それを正確に取り出せるかを測る長文性能テスト。✅ 現在のロード設定では**32,768トークンまでが試験可能範囲**。

**RAG (Retrieval-Augmented Generation / 検索拡張生成)**
外部文書を検索し、その内容を根拠として回答させる構成。埋め込みモデルはこの検索部分で使う。

**ハルシネーション (hallucination)**
モデルが事実でない内容をもっともらしく生成する現象。

**忠実性 (faithfulness)**
RAGにおいて、回答が与えられた文書の内容に忠実か（勝手に補完していないか）を測る指標。

**RAGAS**
RAGパイプラインの評価フレームワーク。忠実性や回答関連性などを自動で採点する。

**構造化出力の準拠率**
JSONスキーマ等の指定形式をどれだけ守れるかの割合。⚠️ **ローカルLLMを実務で使う際に最も効く指標のひとつ。** 同じリクエストを多数回投げて有効率を測る。

## 9.4 計測の信頼性

**決定論 (determinism) / 再現性 (reproducibility)**
同じ入力に同じ出力が返るか。⚠️ **GPU上では `temperature: 0` かつ seed固定でも完全な再現は保証されない。**

**試行数 (n)**
同一条件での実行回数。1回の結果で断定しない。⚠️ 少数サンプルなら**「n=5 での印象」と明記する**のが誠実な書き方。

# 10. APIレスポンスの読み方（実例）

`/v1/chat/completions` の返却例と各フィールドの意味。

```json
{
  "id": "chatcmpl-...",                    // このリクエストの識別子
  "model": "ornith-1.0-35b",               // 実際に応答したモデル
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "PONG",                   // 最終回答（ユーザーに見せる部分）
      "reasoning_content": "Here is ...",  // 思考過程（reasoningモデルのみ）
      "tool_calls": []                     // ツール呼び出しの要求があればここ
    },
    "finish_reason": "stop"                // "stop"=正常終了 / "length"=打ち切り
  }],
  "usage": {
    "prompt_tokens": 16,
    "completion_tokens": 151,
    "total_tokens": 167,
    "completion_tokens_details": { "reasoning_tokens": 146 }
  }
}
```

⚠️ **注意すべき組み合わせ**: `finish_reason: "length"` かつ `content: ""` は**モデルの失敗ではなく `max_tokens` 設定の不足**。思考で枠を使い切っている。
