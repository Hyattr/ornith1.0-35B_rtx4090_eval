# 「入力は速いのに出力は遅い」のはなぜか - LLMのトークンを基本から解説

ChatGPT や Claude 等の LLM サービスを使う中で、ごく当たり前に受け入れているけど理屈はよくわかってないことが意外とあるのではないでしょうか。

- 文字がパラパラと少しずつ出てくる
- 長い資料を貼り付けても一瞬で読み込まれるのに、長い返事を書かせると異様に遅い
- 会話を続けていくと、途中から様子がおかしくなる
- 「考えてから答える」 Thinking モデルは、料金も時間も跳ね上がる

これらは全部、**同じ1つの仕組み**から出てきます。仕組みのほうを知ってしまえば、実際に目にする不思議なことを全部まとめて理解することができます。

この記事では、「LLM は毎日使っているけれど、中で何が起きているかは知らない」くらいの方を対象に、専門用語や難しい数式、モデルの内部構造をなるべく使わずに**トークン**という基本概念をスタート地点にして LLM のことを解説します。

---

## 1. トークンって何？

トークンとは、文字でも単語でもない、ちょうどその中間くらいの**文字の断片**のことです。日本語なら1〜2文字ぶん、英語なら単語1つか、その一部くらいの大きさになります。

```
"こんにちは、元気ですか"  →  ["こんにちは", "、", "元気", "です", "か"]
```

（※あくまでイメージです。実際の分割はモデルごとに違います）

LLM は文字をそのままの形で扱うことができません。そのため、受け取った文章を必ずこの断片の列に分解してから読みはじめます。**トークンは、LLM にとっての「1文字」にあたる単位**だと考えてください。料金も、処理の速さも、扱える量の上限も、すべてこのトークンという単位で数えられています。

この先に出てくる話は、突き詰めればほとんどが「トークンがいくつあって、それがどの順番で処理されるか」の話です。

---

## 2. LLM がやっていることは、たった1つ

LLM が内部でやっていることは、驚くほど単純です。**「ここまでのトークンの並びを見て、次に来る1トークンを当てる」**。本当にこれだけです。

```
入力: ["日本", "の", "首都", "は"]
   ↓
出力: "東京"
```

長い文章をすらすら書いているように見えますが、実際にはこの予測を1回ずつ繰り返しているだけです。

```
["日本","の","首都","は"]                → "東京"
["日本","の","首都","は","東京"]          → "です"
["日本","の","首都","は","東京","です"]    → "。"
```

自分が出したトークンを列の末尾に付け足して、また次の1トークンを当てる。その繰り返しです。

ここで押さえておきたいのは、**入力と出力は別物ではなく、1本の列の前半と後半でしかない**ということです。モデルから見れば、あなたが書いた部分と自分が書いた部分に本質的な区別はありません。どちらも同じ1本の列の一部です。

チャット画面で文字がパラパラと出てくるあの挙動は、人間らしく見せるための演出ではありません。**本当に1トークンずつしか作れていない**から、ああなっているのです。

---

## 3. 読むのは一括、書き出すのは1トークンずつ

2章の仕組みからは、処理が自然と2つの段階に分かれることが導かれます。

### 前半：入力を読む

あなたが送った文章（プロンプト、つまりモデルへの指示文のことです）は、モデルにとって**最初から全部わかっている**ものです。だから全トークンを**まとめて同時に**処理できます。1,000トークンの文章なら、1,000トークンをいっぺんに流し込めます。

### 後半：出力を作る

一方こちらは、**1トークンずつしか作れません**。「東京」を確定させないことには、その次に何が来るかを予測するための材料が揃わないからです。前から順番に決めていくしかないので、**どれだけ高性能な機材を並べても、この部分だけは同時に処理できません**。

この2つは処理にかかる負荷や時間が大きく異なります。使うモデルや機材によって数字は変わりますが、おおよその桁でいうと次のようになります。

| | 速度の桁 |
|---|---|
| 入力を読む | **毎秒 数千トークン** |
| 出力を作る | **毎秒 百〜数百トークン** |

同じモデルを同じマシンで動かしていても、読むときと書くときとで数十倍の開きが出るわけです。ここから、日々の使い方に直結する結論が3つ出てきます。

**プロンプトが長いことは、待ち時間としてはたいして重くありません。** 数千トークンの資料を丸ごと貼り付けても、読み込み自体は1秒前後で終わります。長い前提を渡すことを、速度の面で怖がる必要はありません。

**待ち時間の正体は、ほぼ出力の長さです。** 「詳しく説明して」と頼むと遅くなるのは、モデルが悩んでいるからではありません。単純に、作るトークン数が多くて、生成するのに時間がかかっているからです。なので、すぐに答えが欲しいときは「3行で」「要点だけ」のように、回答の長さを短くするように指定するのが効果的です。

**最初の1文字が表示されるまでの時間は、入力を読み終えるまでの時間とほぼ同じです。** 入力を全部読み終わってようやく1トークン目が予測できるようになるので、当然そうなります。この時間は、入力が長くなるほど比例して伸びていきます。英語では TTFT(Time To First Token) と言います。 この見方を覚えると、「送信してから最初の文字が出るまで」は読んでいる時間、「そこから先」は書いている時間、というふうに切り分けて眺められるようになります。

## 4. コンテキスト長 — 会話全体が入る器

入力と出力が1本の列だと分かると、次に気になるのは「その列は、どこまで長くできるのか」という点だと思います。

これにも上限があり、**コンテキスト長**と呼びます。

```
コンテキスト長 ＝ 入力トークン ＋ 出力トークン
```

ここで大事なのは、これが1回のやりとりだけの上限ではない、という点です。というのも、チャットでは毎回、過去のやりとりを全部まとめてモデルに送り直しているからです。モデルは前回話した内容を覚えているわけではありません。毎回、会話の最初から全部を読み直しているだけなのです。

```
1往復目に送るもの: [システム指示][質問1]
2往復目に送るもの: [システム指示][質問1][回答1][質問2]
3往復目に送るもの: [システム指示][質問1][回答1][質問2][回答2][質問3]
                   ~~~~~~~~~~~~~~ 毎回この全部を送り直している
```

図の先頭にある「システム指示」は、サービス側が裏で付け加えている、モデルの役割や振る舞いを決めるための指示文です。ユーザーからは見えませんが、これも毎回きちんと送られています。

つまり、**会話が続けば続くほど、1回あたりの入力が長くなっていきます**。器の大きさは変わらないのに中身だけが増えていくので、いずれ入り切らなくなります。

長い会話の途中から「最初のほうに出した指示を忘れる」ように見えるのは、モデルが忘れたからではありません。**器から溢れた古い部分が、モデルに送られる前に捨てられている**のです。古い発言から順に切り落とす、要約して詰め直すなど、あふれた分の扱い方はサービスによって変わります。

対策は、**話題が変わったら、新しい会話を始める**ことです。 いろんなトピックについて長く会話を続けるより速く、正確で、しかも安く上がります。

## 5. `max_tokens` — 出力するトークン数の上限

LLM を API 経由で使ったり、ローカル環境で動かしたりする場合には、コンテキスト長とは別に、**`max_tokens`** という設定を考慮する必要があります。ツールによっては「最大出力トークン数」などと表示されている項目です。

名前が紛らわしいのですが、この2つは**採用する範囲が違います**。

```
コンテキスト長 : [ 入力 ][ 出力 ]   ← 合計の上限
max_tokens    :        [ 出力 ]   ← 出力だけの上限
```

「上限」と聞くと入力も含まれそうな気がしますが、`max_tokens` のスコープは出力の側だけです。そして見落としやすいのが、**この2つは同時に制限をかけてくる**という点です。

たとえば、コンテキスト長が 32,768 のモデルを使っていて、`max_tokens` に 16,384 を指定したとします。ここで入力として 25,000 トークンを送ると、器の残りは 32,768 から 25,000 を引いた 7,768 しかありません。`max_tokens` にいくら大きな値を書いていても、実際に出せるのはこの 7,768 トークンまでです。

もう1つ、知っておくと得なことがあります。**`max_tokens` はリソースの予約ではなく、あくまで上限だ**ということです。大きい値を指定しても、モデルが 500 トークンで言い終われば、実際に消費されるのは 500 トークンだけ。料金も500トークン分しかかかりません。大きく取ったせいで遅くなったり高くついたりすることはないのです。**つまり絞る意味はほとんどなく、逆に絞りすぎると、次の章で説明する事故が起きます。**

---

## 6. 「考える」のも出力トークン枠を消費する

最近のモデルには、答えを返す前に、内部で下書きのように考えるものがあります（reasoning / thinking などと呼ばれます）。冒頭で触れた Thinking モデルのことです。この**思考の部分も、立派な出力トークン**です。

画面に表示されないので数のうちに入らない気がしますが、しっかり入ります。料金にも、速度にも、そして `max_tokens` の枠にも影響してきます。

```
[ 思考トークン ][ 回答トークン ]
 ←──── 合わせて max_tokens 以内 ────→
```

思考と回答は、**同じ枠を取り合う関係**にあります。枠が足りないと、思考の途中で打ち切られてしまい、**回答が始まる前に出力が終わってしまいます**。

モデルの返事には、本文とは別に「なぜここで止まったのか」を示す項目が付いてきます。枠を使い切って止まった場合、その中身は次のような状態になります。

```
max_tokens: 128
  思考   : 128トークン   ← 全部を思考で使い切った
  回答   : ""            ← 空
  終了理由: "length"（上限に達した）
```

厄介なのは、**これがエラーとして扱われない**ことです。「正常に、上限まで出力しました」という顔をして返ってきます。プログラムから LLM を呼び出している場合（開発者向けの利用方法である API を使う場合）は、中身が空っぽの回答が、正常な結果として渡されて混乱することになります。

そして思考の量は、想像よりずっと多くなります。「「はい」とだけ答えて」というような、ごく単純な指示に対しても、裏側で百数十トークン考えることがあります。**2文字を返すために、その数十倍を考えている**わけです。Thinking モデルを使いながら `max_tokens` を数百に絞ってしまうと、こんな簡単な質問でも意図した出力結果が得られなくなります。

だからこそ、5章の話がここで効いてきます。**Thinking モデルを使うなら、`max_tokens` は思い切って大きく取っておく。** 絞って得することは、何もありません。

## 7. 会話の続きが速いのはなぜか

3章で「入力を読むのにも時間はかかる」と書きました。そうすると、4章の「毎回、会話を全部送り直している」という話が、ひどく無駄に思えてきます。10往復目ともなれば、それまでの9往復分をもう一度読み直すことになるからです。

実際、素直にそのままやると猛烈に無駄です。そこで LLM は、各トークンを読んだときの**途中までの読解結果をメモとして保存しておく**という工夫をしています。

```
1トークン目を作るとき: 入力1,000トークンを読む → 1,000トークン分のメモを保存
2トークン目を作るとき: 保存したメモ(1001トークン分) ＋ 新しい1トークンだけ生成
3トークン目を作るとき: 保存したメモ(1002トークン分) ＋ 新しい1トークンだけ生成
```

このメモが **KVキャッシュ** と呼ばれるものです。「LLM を動かすとメモリを大量に食う」とよく言われますが、その内訳はモデル本体と、このメモの置き場です。コンテキスト長を大きく設定するとメモリ消費が増えるのは、置き場をあらかじめ確保しておくためです。

さらに多くのサービスは、このメモを**返事を書き終えたあとも捨てずに取っておきます**。次の依頼が届いたときに、送られてきた文章を**先頭から見比べて、一致している範囲まで**は前回のメモをそのまま使い回せるからです。使い回せた分は、読み込みの計算がまるごと不要になります。これを**プロンプトキャッシュ**と呼びます。

```
前回: [A][B][C][D][E]      ← メモ済み
今回: [A][B][C][X][Y]
       ~~~~~~~~~ ここまで使い回せる。[X] から計算し直し
```

会話の2往復目以降が、送っている量のわりにすっと始まるのは、このキャッシュが効いているからです。開発者向けの料金表に「キャッシュ入力」という安い単価が用意されているのも、同じ仕組みによるものです。

### キャッシュは先頭が一致すると「ヒット」

ここは少し気を付ける必要があります。**一致の判定は、先頭からの連続した一致でしか成立しません。**

理由は、さきほどのメモの性質にあります。**あるトークンのメモの中身は、「列の何番目にあるか」と「その手前に何があったか」で決まります。** だから途中に1トークン割り込ませると、それより後ろのメモは全部作り直しになってしまうのです。

- 文章の**先頭**を変える → それ以降が全部作り直しになるので、**キャッシュ効果なし**
- 文章の**末尾**を変える → 先頭部分は同じままなので、**途中までは処理不要**

実用上の結論はシンプルです。**変わらないもの（役割の指示、長い資料、共通の前提）を先頭に置き、毎回変わるもの（今回の質問）を末尾に置く。** 同じ資料について何度も質問するなら、順番をこうするだけで、2回目以降が速く、そして安くなります。

逆に、毎回変わる値（現在時刻、その場で作った通し番号、ユーザー名など）をうっかり先頭に混ぜてしまうと、キャッシュは一切効きません。

## 8. 症状から逆引き

ここまでの仕組みを知っていれば説明がつく、よくある症状を並べておきます。

**回答が文の途中でぶつ切りになる**

`max_tokens` が足りていません。返事に付いてくる終了理由が `length` になっているはずなので、上限を上げてください。

**回答が空っぽで返ってくる**

Thinking モデルで `max_tokens` が足りていない可能性が高いです（6章）。エラーにならないので、空の回答が返ってきたら、まずここを疑ってください。

**長い会話の途中から、指示を守らなくなる・話が噛み合わなくなる**

コンテキスト長から溢れています（4章）。会話を新しく作り直すのが、いちばん速い解決策です。

**同じことを何度も聞いているのに、毎回同じだけ待たされる**

プロンプトの先頭に、毎回変わるものが紛れ込んでいないか確認してみてください（7章）。

**とにかく応答が遅い**

入力の長さではなく、出力の長さを疑ってください（3章）。「簡潔に」「3行で」と長さを指定するのが最も効果的です。Thinking モデルの場合は、画面に出ない思考の分だけ、さらに時間がかかります。

## まとめ

この6つだけ持って帰っていただければ十分です。

1. **トークンは文字の断片。** LLM にとっての「1文字」にあたる単位
2. **LLM は「次の1トークンを当てる」を繰り返しているだけ**
3. **入力はまとめて処理できる（速い）／出力は1トークンずつしか作れない（遅い）。** 待ち時間の正体は、ほぼ出力の長さ
4. **コンテキスト長は、入力と出力を合わせた上限。** チャットは毎回、会話を全部送り直している
5. **`max_tokens` は出力だけの上限。思考も出力トークン。** 絞りすぎると空の回答が返る
6. **キャッシュは先頭からの一致でしか効かない。** 変わらないものを前に、変わるものを後ろに

3番が分かると、「なぜ長い文章の生成だけ異様に遅いのか」が理解できるようになります。そして4〜6番は、**エラーにはならないけど結果だけがおかしくなる**性質があるので、LLMの性能評価をする際にはこれを把握しておく必要があります。

## 付録：紛らわしい用語の対比表

この分野は**似た名前で別のものを指す言葉**が多く、そこが最初の壁になります。読み終えたいま見ると、それぞれの違いがはっきりするはずです。

### 入力トークン ↔ 出力トークン

| | 入力トークン | 出力トークン |
|---|---|---|
| 何 | こちらが送った文章 | モデルが書いた文章 |
| 処理 | まとめて同時に | 1トークンずつ順番に |
| 速さ | 速い | **遅い（数十倍の差）** |
| 料金 | 安い | 高い（数倍のことが多い） |

### `max_tokens` ↔ コンテキスト長

| | `max_tokens` | コンテキスト長 |
|---|---|---|
| 縛る範囲 | **出力だけ** | **入力＋出力の合計** |
| 決めるとき | やりとりごとに指定 | モデルを動かすときに固定 |
| 超えたら | 出力が打ち切られる | 古い部分が捨てられる |

### 思考トークン ↔ 回答トークン

| | 思考トークン | 回答トークン |
|---|---|---|
| 画面に出るか | 出ないことが多い | 出る |
| 出力トークンか | **そう** | そう |
| 課金されるか | **される** | される |

### KVキャッシュ ↔ プロンプトキャッシュ

| | KVキャッシュ | プロンプトキャッシュ |
|---|---|---|
| いつ効く | 1回の生成の中で | **やりとりをまたいで** |
| 効果 | 同じ生成の中で読み直しを省く | 2回目以降の読み込みが消える |
| 性質 | 無いと成立しない基盤 | 先頭一致でのみ効く |
