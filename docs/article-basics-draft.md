# 「入力は速いのに出力は遅い」のはなぜか — LLMのトークンを基本から

ローカルLLMの速度を測っていて、自分の計測が二度壊れました。原因を追いかけた結果、**壊れた理由はモデルではなく、私がトークンの扱いを分かっていなかったこと**でした。

同じところでつまずく人は多いと思うので、前提知識のほうを独立させて書きます。専門用語はほぼ使いません。「LLMは使っているけど、中で何が起きているかは知らない」くらいの方を想定しています。

この分野は**似た名前で別のものを指す言葉**が多く、そこが最初の壁になります。なので2章で先に対比表を置きました。分からなくなったらそこに戻ってきてください。

最後まで読むと、**なぜ長い文章の生成だけ異様に遅いのか**、**なぜベンチマークの数字が簡単に嘘になるのか**が分かります。

---

## 1. トークンって何？

文字でも単語でもなく、その中間の**文字の断片**です。日本語なら1〜2文字、英語なら単語1個かその一部くらい。

```
"こんにちは、元気ですか"  →  ["こんにちは", "、", "元気", "です", "か"]
```

（※あくまでイメージです。実際の分割はモデルごとに違います）

LLM は文字をそのまま扱えないので、文章を必ずこの断片の列に分解してから読みます。**トークンは LLM にとっての「1文字」**だと思ってください。料金も速度も制限も、全部この単位で数えられています。

---

## 2. 先に、混同しやすい言葉を並べておく

この分野の用語は、**似た言葉が別のものを指している**のが最大のつまずきどころです。私が計測を二度壊したのも、突き詰めればここの取り違えでした。

まず対比だけ見てください。**いま全部わからなくて大丈夫です。** 3章以降で一つずつ説明するので、「2つあるらしい」とだけ頭に置いてもらえれば十分です。

### ① 入力トークン ↔ 出力トークン

| | 入力トークン | 出力トークン |
|---|---|---|
| 何 | こちらが送った文章 | モデルが書いた文章 |
| 速さ | **速い**（約6,700/秒） | **遅い**（約136/秒） |

同じ「トークン」でも、**速度が約50倍違います**。まとめて処理できるか、1個ずつしか作れないかの差です（→4章）。

### ② `max_tokens` ↔ コンテキスト長

どちらも「トークン数の上限」ですが、**縛る範囲が違います**。

| | `max_tokens` | コンテキスト長 |
|---|---|---|
| 縛る範囲 | **出力だけ** | **入力＋出力の合計** |
| 決めるとき | リクエストごとに指定 | モデルを読み込むときに固定 |

「上限」と聞いて入力も含むと思うと混乱します。**入力まで含む上限はコンテキスト長のほう**です（→7章）。

### ③ 思考トークン ↔ 回答トークン

最近のモデルは、答える前に内部で下書きのように考えます。**この思考も出力トークンです。**

| | 思考トークン | 回答トークン |
|---|---|---|
| 画面に出るか | 出ないことが多い | 出る |
| 出力トークンか | **そう** | そう |

そして両者は **`max_tokens` の枠を取り合います**。「見えないから数に入らない」と思うと事故ります（→7章）。

### ④ KVキャッシュ ↔ プロンプトキャッシュ

名前が似ていますが、**生きている時間が違います**。

| | KVキャッシュ | プロンプトキャッシュ |
|---|---|---|
| いつ使う | 1回の生成の中で | **リクエストをまたいで** |
| 効果 | 同じ生成の中で読み直しを省く | 2回目以降の読み込みが消える |
| 落とし穴 | VRAMを食う | **計測が静かに壊れる** |

前者は無いと成立しない基盤技術、後者は**あなたのベンチマークを嘘にする犯人**です（→5章・6章）。

---

このうち**③の取り違えで「モデルが悪い」という誤った結論**が出て、**④の取り違えで「物理的にありえない速度」**が出ます。私が実際にやったのはこの2つです。②は踏みませんでしたが、長い資料を読ませる用途なら次に待っている罠です。

以下、順に見ていきます。

---

## 3. LLM がやっていることは、たった1つ

**「ここまでのトークン列を見て、次の1トークンを当てる」**。これだけです。

```
入力: ["日本", "の", "首都", "は"]
   ↓
出力: "東京"
```

長い文章を書いているように見えますが、実際は**これを1回ずつ繰り返している**だけです。

```
["日本","の","首都","は"]               → "東京"
["日本","の","首都","は","東京"]        → "です"
["日本","の","首都","は","東京","です"]  → "。"
```

自分が出したトークンを列の末尾に足して、また次を当てる。ここで大事なのは、**入力と出力は別物ではなく、1本の列の前半と後半でしかない**ということです。

チャット画面で文字がパラパラと出てくるあの挙動は、演出ではありません。**本当に1個ずつしか作れていない**のです。

---

## 4. だから処理が2段階に分かれる

### 前半（入力の読み込み）

あなたが送ったプロンプトは、**最初から全部わかっています**。だから全トークンを**まとめて同時に**処理できます。1,000トークンあっても1,000個いっぺんに流せる。

### 後半（出力の生成）

こちらは**1個ずつしか作れません**。「東京」を確定させないと、その次を予測するための材料が揃わないからです。**原理的に、どうやっても並列化できない**。

この差が、そのまま実測値に出ます。手元の環境（RTX 4090 + 35Bのモデル）で測った値です。

| | 速度 |
|---|---:|
| 入力の読み込み | **約 6,700 トークン/秒** |
| 出力の生成 | **約 136 トークン/秒** |

**同じモデル、同じGPUで、約50倍の差**。

ここから実用的な話が2つ出てきます。

**「プロンプトが長い」のは、待ち時間としては軽い。** 4,000トークンの資料を貼っても、読み込みは1秒かかりません。

**待ち時間の正体は、ほぼ出力の長さ。** 「詳しく説明して」と頼むと遅いのは、モデルが悩んでいるからではなく、単に作るトークン数が多いからです。

そしてもう1つ。**最初の1文字が出るまでの時間は、入力を全部読み終わる時間とほぼ同じ**です。読み終わらないと1個目を予測できないので。実測でも、入力316トークンなら0.09秒、25,669トークンなら3.78秒と、入力の長さにほぼ比例して伸びました。

---

## 5. 「読解メモ」を取っている

ここで素朴な疑問が出ます。

> 出力するたびに「ここまでの列」を丸ごと入れ直すなら、100個目を作るときは99個分を読み直すことになる。無駄では？

その通りで、**素直にやると猛烈に無駄**です。なので実際のLLMは、各トークンを読んだときの**中間的な読解結果**をメモして保存しています。

```
1個目を作るとき: 入力1,000個を読む → 1,000個分のメモを保存
2個目を作るとき: メモ1,000個 ＋ 新しい1個だけ  ← 読み直さない
3個目を作るとき: メモ1,001個 ＋ 新しい1個だけ
```

これが **KVキャッシュ** と呼ばれるものです。「モデルを動かすとVRAMを食う」という話の、重み以外のもう半分がこれです。

ここで1つだけ覚えてほしい性質があります。**あるトークンのメモは「列の何番目にあるか」と「その前に何があったか」で決まる**。だから途中に1個割り込ませると、**それ以降のメモは全部作り直し**になります。

---

## 6. メモは、次のリクエストにも残る

このメモは本来「1回の生成の間だけ」のものですが、多くの推論サーバーは**生成が終わっても捨てずに取っておきます**。

次のリクエストが来たとき、**先頭から見比べて一致する範囲まで**は前回のメモを使い回せる。使い回せた分は読み込みの計算が丸ごと消えます。これを**プロンプトキャッシュ**と呼びます。

```
前回: [A][B][C][D][E]      ← メモ済み
今回: [A][B][C][X][Y]
       ~~~~~~~~~ ここまで使い回せる。[X] から計算し直し
```

4章の性質から、**一致判定は先頭からの連続一致でしか成立しません**。ここが直感に反するところで、

- **先頭**を変える → キャッシュは効かない
- **末尾**を変える → 先頭は同じままなので、**バッチリ効く**

同じプロンプトを2回投げて、1回目と2回目を比べた実測がこれです。

| 入力トークン | 1回目 | 2回目 | 高速化 |
|---:|---:|---:|---:|
| 1,093 | 0.220秒 | 0.057秒 | 3.9倍 |
| 4,306 | 0.639秒 | 0.057秒 | 11.2倍 |
| 17,115 | 2.470秒 | 0.060秒 | **41.0倍** |

注目すべきは、**2回目が入力の長さに関係なく約0.06秒で一定**なことです。読み込みの計算がゼロになっているので、当然そうなります。そして**入力が長いほど、本来の値との乖離が広がる**。

これが「計測が壊れた」1つ目です。速度を測るつもりで同じプロンプトを5回投げていたので、2回目以降は**実態の1/41の時間**を「計測結果」として記録していました。**エラーは一切出ません。ただ速い数字が出るだけです。**

さらに、ダミーの長文を共通の雛形から作っていたせいで、24,000トークンのプロンプトが16,000トークンのプロンプトを**先頭にまるごと含んでいました**。別の条件なのにキャッシュが効いてしまい、「24,000トークンのほうが16,000トークンより速い」という物理的にありえない結果が出ていました。

---

## 7. 「考える」のも出力トークンを食う

最近のモデルには、答える前に内部で下書きのように考える（reasoning / thinking）ものがあります。この**思考も、立派な出力トークン**です。

APIには `max_tokens` という「出力の上限」を指定する項目がありますが、思考と回答は**この同じ枠を取り合います**。

```
[ 思考トークン ][ 回答トークン ]
 ←──── 合わせて max_tokens 以内 ────→
```

枠が足りないと、思考の途中で打ち切られ、**回答が始まる前に終了します**。

「PONG とだけ答えて」と頼んだときの実際のレスポンスです。まず、上限に余裕がある場合。

```
思考   : 146トークン
回答   : "PONG"
終了理由: "stop"（言い終わった）
```

**4文字を出すために、裏で146トークン考えています。** では上限を 128 に絞ると、こうなります。

```
出力の上限: 128
思考   : 128トークン   ← 全部を思考で使い切った
回答   : ""            ← 空
終了理由: "length"（上限に達した）
```

**エラーではありません。** 「正常に、上限まで出力しました」というレスポンスとして返ってきます。

上限を変えて、回答が空になる割合を測りました（各5回）。

| 出力の上限 | 「PONGと答えて」 | 中程度の課題 |
|---:|---:|---:|
| 64 | 100% | 100% |
| 128 | 60% | 100% |
| 256 | **0%** | 100% |
| 512 | 0% | 60% |
| 1024 | 0% | **0%** |

**「PONGと答えて」に256トークンの枠が要ります。**

これが「計測が壊れた」2つ目です。この表から「難しい問題なら4,096あれば十分だろう」と見積もってコード生成を12問解かせたところ、**12問中4問が枠の上限に達しました**。うち3問は回答が完全に空、1問は途中で切れています。しかも空になった1問は、そのセットで**最も簡単な問題**でした。

空の回答は採点で最低点になります。結果、平均は5点満点で3.58。上限を16,384に上げて回し直したら **4.75** でした。**測っていたのはモデルの実力ではなく、私の設定ミスでした。**

### もう一つの上限 — コンテキスト長

2章の②の話です。

```
コンテキスト長（例: 32,768） ＝ 入力トークン ＋ 出力トークン
```

「出力の上限を16,384にした」つもりでも、**入力を25,000トークン送っていたら、実際に出せるのは残りの7,768だけ**です。しかもこの打ち切りも終了理由 `length` で返るので、**枠不足と見分けがつきません**。

長い資料を読ませる用途なら、出力の上限は固定値ではなく「コンテキスト長 − 入力の長さ − 余裕」で計算するのが安全です。

（なお、出力の上限は**予約ではなく上限**です。16,384を指定してもモデルが500で止まれば消費は500。大きく取ること自体のコストはありません。私は「大きくすると重くなりそう」と絞って事故を起こしました）

## 8. どうやって気づくか

ここが一番お伝えしたいところです。どちらの事故も**エラーが出ません**。手がかりは数字の中にしかありません。

**キャッシュに汚染されているサイン**

> 入力の長さを変えているのに、最初の1文字までの時間が**ほぼ一定**

一定になったら計算してみてください。17,000トークンを0.06秒で処理したなら、それは毎秒28万トークン。**物理的にありえない値なら、測れていません。** 対策は、実行ごとにプロンプトの**先頭**を一意にすること（末尾では効きません）。

**出力の枠が足りていないサイン**

> 終了理由が `length` で、かつ回答が**空**。思考トークン数が**上限に張り付いている**

思考トークン数が毎回きれいに上限と同じ値なら、それは「ちょうど使い切った」のではなく「**足りていない**」です。評価スクリプトを書くなら、この条件を**失敗として弾く処理**を必ず入れてください。入れないと、自分の設定ミスがモデルの点数として記録されます。

（細かい注意として、ツールを呼び出したときも回答は空になりますが、そちらは正常動作です。終了理由で区別できます）

---

## まとめ

この6行だけ持って帰っていただければ十分です。

1. **トークンは文字の断片。** LLMにとっての「1文字」
2. **LLMは「次の1トークンを当てる」を繰り返しているだけ**
3. **入力はまとめて処理できる（速い）／出力は1個ずつしか作れない（遅い）。** 実測で約50倍差
4. **`max_tokens` は出力だけの上限。入力まで含む上限はコンテキスト長**
5. **思考も出力トークン。** 回答と同じ枠を取り合う
6. **読解メモを先頭から使い回すのがキャッシュ。** 末尾を変えても効いてしまう

3番が分かると「なぜ長文生成だけ遅いのか」が腑に落ちます。そして4〜6番は、**エラーを出さずに数字だけを狂わせる**ので、ベンチマークを取る側には致命的です。

私は両方を踏んで、片方は「物理的にありえない数字」で、もう片方は**危うく気づかないまま**公開するところでした。
