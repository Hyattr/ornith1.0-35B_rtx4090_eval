# 「入力は速いのに出力は遅い」のはなぜか - LLMのトークンを基本から解説

ChatGPT や Claude 等の LLM サービスを使う中で、ごく当たり前に受け入れているけど理屈はよくわかってないことが意外とあるのではないでしょうか。

- 文字がパラパラと少しずつ出てくる
- 長い資料を貼り付けても一瞬で読み込まれるのに、長い返事を書かせると異様に遅い
- 会話を続けていくと、途中から様子がおかしくなる
- 「考えてから答える」 Thinking モデルは、料金も時間も跳ね上がる

これらは全部、**同じ1つの仕組み**から出てきます。仕組みのほうを知ってしまえば、実際に目にする不思議なことを全部まとめて理解することができます。

この記事では、「LLM は毎日使っているけれど、中で何が起きているかは知らない」くらいの方を対象に、専門用語や難しい数式、モデルの内部構造をなるべく使わずに**トークン**という基本概念スタート地点にして LLM のことを解説します。

---

## 1. トークンって何？

文字でも単語でもなく、その中間の**文字の断片**です。日本語なら1〜2文字、英語なら単語1個かその一部くらい。

```
"こんにちは、元気ですか"  →  ["こんにちは", "、", "元気", "です", "か"]
```

（※あくまでイメージです。実際の分割はモデルごとに違います）

LLM は文字をそのまま扱えないので、文章を必ずこの断片の列に分解してから読みます。**トークンは LLM にとっての「1文字」**だと思ってください。料金も速度も上限も、全部この単位で数えられています。

以降に出てくる話は、ほぼ全部「そのトークンが何個で、いつ処理されるか」の話です。

---

## 2. LLM がやっていることは、たった1つ

**「ここまでのトークン列を見て、次の1トークンを当てる」**。これだけです。

```
入力: ["日本", "の", "首都", "は"]
   ↓
出力: "東京"
```

長い文章を書いているように見えますが、実際は**これを1回ずつ繰り返している**だけです。

```
["日本","の","首都","は"]                → "東京"
["日本","の","首都","は","東京"]          → "です"
["日本","の","首都","は","東京","です"]    → "。"
```

自分が出したトークンを列の末尾に足して、また次を当てる。ここで大事なのは、**入力と出力は別物ではなく、1本の列の前半と後半でしかない**ということです。モデルから見れば、あなたが書いた部分と自分が書いた部分の区別は本質的ではありません。ただの1本の列です。

チャット画面で文字がパラパラと出てくるあの挙動は、演出ではありません。**本当に1個ずつしか作れていない**のです。

---

## 3. 読むのは一括、書き出すのは1トークンずつ

2章から、処理が自然に2段階に分かれます。

### 前半：入力を読む

あなたが送ったプロンプトは、**最初から全部わかっています**。だから全トークンを**まとめて同時に**処理できます。1,000トークンあっても1,000個いっぺんに流せる。

### 後半：出力を作る

こちらは**1個ずつしか作れません**。「東京」を確定させないと、その次を予測するための材料が揃わないからです。**原理的に、どうやっても並列化できない**。

この差は誤差のレベルではありません。環境によりますが、ざっくり

| | 速度の桁 |
|---|---|
| 入力を読む | **毎秒 数千トークン** |
| 出力を作る | **毎秒 百〜数百トークン** |

**同じモデル、同じマシンで、数十倍の開き**が出ます。ここから実用的な結論が3つ出てきます。

**「プロンプトが長い」のは、待ち時間としては軽い。** 数千トークンの資料を貼り付けても、読み込み自体は1秒前後で終わります。長い前提を渡すことを、速度の面で怖がる必要はありません。

**待ち時間の正体は、ほぼ出力の長さ。** 「詳しく説明して」と頼むと遅いのは、モデルが悩んでいるからではありません。単に作るトークン数が多いからです。急ぎたいなら「3行で」と指定するのがいちばん効きます。

**最初の1文字が出るまでの時間は、入力を読み終わる時間とほぼ同じ。** 読み終わらないと1個目を予測できないので当然です。この時間は入力の長さにほぼ比例して伸びます。「送信してから最初の文字が出るまでの間」は読んでいる時間、「そこから先」は書いている時間、と分けて見られるようになります。

## 4. コンテキスト長 — 会話全体が入る器

入力と出力が1本の列だと分かると、次の疑問が出ます。**その列は、どこまで長くできるのか。**

上限があります。これが**コンテキスト長**です。

```
コンテキスト長 ＝ 入力トークン ＋ 出力トークン
```

ここで重要なのは、これが**1回のやりとりの上限ではない**ことです。チャットでは、過去のやりとり全部をもう一度モデルに送り直しています。モデルは前回の会話を覚えていません。毎回、最初から全部読み直しているだけです。

```
1往復目に送るもの: [システム指示][質問1]
2往復目に送るもの: [システム指示][質問1][回答1][質問2]
3往復目に送るもの: [システム指示][質問1][回答1][質問2][回答2][質問3]
                   ~~~~~~~~~~~~~~ 毎回この全部を送り直している
```

つまり**会話が続くほど、毎回の入力が長くなっていきます**。器の大きさは変わらないのに中身が増えるので、いずれ入り切らなくなる。

長い会話で「最初のほうの指示を忘れる」のは、モデルが忘れたのではありません。**器から溢れた古い部分が、送られる前に捨てられている**のです。ツールによって、古い発言から順に切り落とす、要約して詰め直す、などの処理が入ります。

対策も同じ理屈から出ます。**話題が変わったら新しい会話を始める。** 長い会話を続けるより速く、安く、正確です。

---

## 5. `max_tokens` — 出力するトークン数の上限

コンテキスト長とは別に、**`max_tokens`** という設定があります（ツールによっては「最大出力トークン数」などと表示されます）。

紛らわしいのですが、この2つは**縛る範囲が違います**。

```
コンテキスト長 : [ 入力 ][ 出力 ]   ← 合計の上限
max_tokens    :        [ 出力 ]   ← 出力だけの上限
```

「上限」と聞くと入力も含みそうですが、`max_tokens` は**出力だけ**です。そして重要なのは、**両方が同時に効く**ということ。

`max_tokens` を 16,384 に設定していても、コンテキスト長が 32,768 で入力を 25,000 トークン送っていたら、実際に出せるのは残りの **7,768 だけ**です。器の空きが足りません。

もう1つ、覚えておくと得なことがあります。**`max_tokens` は予約ではなく上限です。** 大きい値を指定しても、モデルが 500 トークンで言い終われば消費は 500 です。料金も 500 分。「大きく取ると遅くなる/高くなる」ということはありません。**絞る意味はほとんどなく、絞りすぎると次章の事故が起きます。**

---

## 6. 「考える」のも出力トークン枠を消費する

最近のモデルには、答える前に内部で下書きのように考えるもの（reasoning / thinking）があります。この**思考も、立派な出力トークン**です。

画面に出ないので数に入らない気がしますが、入ります。料金にも、速度にも、そして `max_tokens` の枠にも。

```
[ 思考トークン ][ 回答トークン ]
 ←──── 合わせて max_tokens 以内 ────→
```

思考と回答は**同じ枠を取り合います**。枠が足りないと、思考の途中で打ち切られ、**回答が始まる前に終了します**。

```
max_tokens: 128
  思考   : 128トークン   ← 全部を思考で使い切った
  回答   : ""            ← 空
  終了理由: "length"（上限に達した）
```

厄介なのは、**これがエラーにならない**ことです。「正常に、上限まで出力しました」というレスポンスとして返ってきます。API を直接叩いている場合、空文字列が正常な返り値として渡ってくるだけです。

そして思考の量は、想像よりずっと多いです。「PONG とだけ答えて」のような些細な指示でも、裏で百数十トークン考えることがあります。**4文字の回答に、その数十倍の思考**です。思考するモデルで `max_tokens` を数百に絞ると、簡単な質問でも空振りします。

だから5章の結論がここに効いてきます。**思考するモデルを使うなら、`max_tokens` は思い切って大きく取る。** 絞って得することは何もありません。

---

## 7. 会話の続きが速いのはなぜか

3章で「入力を読むのにも時間はかかる」と書きました。だとすると、4章の「毎回、会話全部を送り直している」は無駄に思えます。10往復目には、9往復分をもう一度読み直すことになる。

その通りで、**素直にやると猛烈に無駄**です。なので実際の LLM は、各トークンを読んだときの**中間的な読解結果をメモして保存**しています。

```
1個目を作るとき: 入力1,000個を読む → 1,000個分のメモを保存
2個目を作るとき: メモ1,000個 ＋ 新しい1個だけ  ← 読み直さない
3個目を作るとき: メモ1,001個 ＋ 新しい1個だけ
```

これが **KVキャッシュ** と呼ばれるものです。「LLM を動かすとメモリを食う」という話の、モデル本体以外のもう半分がこれです。コンテキスト長を大きく設定するとメモリ消費が増えるのは、この置き場をあらかじめ確保するためです。

そして多くのサービスは、このメモを**生成が終わっても捨てずに取っておきます**。次のリクエストが来たとき、**先頭から見比べて一致する範囲まで**は前回のメモを使い回せる。使い回せた分は、読み込みの計算が丸ごと消えます。これを**プロンプトキャッシュ**と呼びます。

```
前回: [A][B][C][D][E]      ← メモ済み
今回: [A][B][C][X][Y]
       ~~~~~~~~~ ここまで使い回せる。[X] から計算し直し
```

会話の2往復目以降が、送っている量のわりに速く始まるのはこれです。API の料金表に「キャッシュ入力」という安い単価があるのも、同じ仕組みです。

### キャッシュは先頭が一致すると"ヒット"

ここが直感に反するところです。**一致判定は、先頭からの連続一致でしか成立しません。**

理由は5章のメモの性質にあります。**あるトークンのメモは「列の何番目にあるか」と「その前に何があったか」で決まります。** だから途中に1個割り込ませると、それ以降のメモは全部作り直しになる。

- **先頭**を変える → それ以降が全部作り直し。**まったく効かない**
- **末尾**を変える → 先頭は同じまま。**バッチリ効く**

実用上の結論はシンプルです。**変わらないもの（システム指示、長い資料、共通の前提）を先頭に置き、毎回変わるもの（今回の質問）を末尾に置く。** 同じ資料について何度も質問するなら、この順番にするだけで2回目以降が速く安くなります。

逆に、毎回変わる値（日時、乱数、ユーザー名）を先頭に混ぜると、キャッシュは一切効きません。

## 8. 症状から逆引き

ここまでの仕組みで説明がつく、よくある症状です。

**回答が文の途中でぶつ切りになる**
→ `max_tokens` 不足。終了理由が `length` になっているはずです。上限を上げてください。

**回答が空で返ってくる**
→ 思考するモデルで `max_tokens` が足りていません（6章）。エラーにならないので、空文字列が返ったら疑ってください。

**長い会話の途中から、指示を守らなくなる/話が噛み合わなくなる**
→ コンテキスト長から溢れています（4章）。会話を作り直すのが最速の解決です。

**同じことを何度も聞いているのに毎回遅い**
→ プロンプトの先頭に、毎回変わるものが入っていないか確認（7章）。

**とにかく応答が遅い**
→ 入力の長さではなく、出力の長さを疑ってください（3章）。「簡潔に」「N行で」の指定が最も効きます。思考するモデルなら、思考の分も含めて遅くなります。

---

## まとめ

この6行だけ持って帰っていただければ十分です。

1. **トークンは文字の断片。** LLM にとっての「1文字」
2. **LLM は「次の1トークンを当てる」を繰り返しているだけ**
3. **入力はまとめて処理できる（速い）／出力は1個ずつしか作れない（遅い）。** 待ち時間の正体はほぼ出力の長さ
4. **コンテキスト長は入力＋出力の合計の上限。** チャットは毎回、会話全部を送り直している
5. **`max_tokens` は出力だけの上限。思考も出力トークン。** 絞ると空の回答が返る
6. **キャッシュは先頭からの一致でしか効かない。** 変わらないものを前に、変わるものを後ろに

3番が分かると「なぜ長文生成だけ遅いのか」が腑に落ちます。4〜6番は、**エラーを出さずに結果だけを静かに狂わせる**ので、知らないと原因にたどり着けません。

## 付録：紛らわしい用語の対比表

この分野は**似た名前で別のものを指す言葉**が多く、そこが最初の壁になります。読み終えたいま見ると、違いがはっきりするはずです。

### 入力トークン ↔ 出力トークン

| | 入力トークン | 出力トークン |
|---|---|---|
| 何 | こちらが送った文章 | モデルが書いた文章 |
| 処理 | まとめて同時に | 1個ずつ順番に |
| 速さ | 速い | **遅い（数十倍の差）** |
| 料金 | 安い | 高い（数倍のことが多い） |

### `max_tokens` ↔ コンテキスト長

| | `max_tokens` | コンテキスト長 |
|---|---|---|
| 縛る範囲 | **出力だけ** | **入力＋出力の合計** |
| 決めるとき | リクエストごとに指定 | モデルを動かすときに固定 |
| 超えたら | 出力が打ち切られる | 古い部分が捨てられる |

### 思考トークン ↔ 回答トークン

| | 思考トークン | 回答トークン |
|---|---|---|
| 画面に出るか | 出ないことが多い | 出る |
| 出力トークンか | **そう** | そう |
| 課金されるか | **される** | される |

### KVキャッシュ ↔ プロンプトキャッシュ

| | KVキャッシュ | プロンプトキャッシュ |
|---|---|---|
| いつ効く | 1回の生成の中で | **リクエストをまたいで** |
| 効果 | 同じ生成の中で読み直しを省く | 2回目以降の読み込みが消える |
| 性質 | 無いと成立しない基盤 | 先頭一致でのみ効く |
